Flax — reading the code, not just running it

Chapter 11. In PyTorch the weights live inside the module object. In Flax they do not, and every strange thing about Flax code follows from that one fact. This chapter is about being able to open an unfamiliar Flax file and say what every line does.

The one strange thing, as a printed artifact

Start familiar — pt a linear layer in PyTorch

import torch lin = torch.nn.Linear(2, 3) print(lin) print("lin.weight.shape :", tuple(lin.weight.shape)) print("lin.bias.shape :", tuple(lin.bias.shape)) print("state_dict keys :", list(lin.state_dict().keys()))
output — real run, torch 2.8.0 Linear(in_features=2, out_features=3, bias=True) lin.weight.shape : (3, 2) lin.bias.shape : (3,) state_dict keys : ['weight', 'bias']

Nothing surprising. The object is the model: it carries its own numbers, you can reach in and read them, and state_dict() is a view onto the numbers the object already holds.

The same layer in jx Flax — and the line that fails

import jax, jax.numpy as jnp from flax import linen as nn model = nn.Dense(features=3) print(model) try: model.kernel except Exception as e: print(f"{type(e).__name__}: {e}")
output — real run, flax 0.12.9 (trimmed: the repr lists 10 attributes, 5 shown) Dense( # attributes features = 3 use_bias = True dtype = None param_dtype = float32 kernel_init = init ) AttributeError: "Dense" object has no attribute "kernel". If "kernel" is defined in '.setup()', remember these fields are only accessible from inside 'init' or 'apply'.

Read the repr first. Every line in it is a setting: how many outputs, which dtype, which initializer function. There is not a single number that could be trained. Read the error second, because it is unusually helpful: it does not say "no such thing as kernel", it says the kernel is only reachable inside two specific functions.

So where are they? You have to ask for them

x = jnp.ones((1, 2)) # one example, 2 features params = model.init(jax.random.key(0), x) # <- this is where numbers get made print(type(params).__name__) print(jax.tree.map(jnp.shape, params))
output — real run dict {'params': {'bias': (3,), 'kernel': (2, 3)}}

Line by line. jax.tree.map walks a nested structure and applies a function to every array at the leaves, so mapping jnp.shape over the result prints the skeleton instead of pages of floats. The type is a plain dict. Inside it, one entry called params, and inside that, the two arrays.

Two details worth pinning now. The kernel is (2, 3), which is (inputs, outputs) — the transpose of torch's (3, 2), so a naive weight copy between the two frameworks is silently wrong. And init needed x: the layer was told it has 3 outputs but never told it has 2 inputs, so it has to see a real input to know the shape to create. Page 1 shows exactly how it finds out.

The whole chapter in one sentence

You now have two objects where PyTorch has one:

  • the module — a recipe. Settings and code, zero numbers. Cheap, reusable, and it never changes during training.
  • the params dict — numbers. No code, no idea what it is for. This is the thing that gets differentiated, updated, sharded and checkpointed.

And one function that puts them together for exactly one call: model.apply(params, x). Chapter 6 said it in one line, which now has something concrete under it: a neural network library in JAX is a convenient factory and namer for that pytree.

self.param is one line that does two different things

Step 1 — the smallest possible module

Course canonical numbers: w = 2, x = 3, target t = 10. One weight, one multiply, no layers, no bias.

def make_w(key): print(" [init_fn] creating w = 2.0") return jnp.array(2.0) class Times(nn.Module): @nn.compact def __call__(self, x): print(" [body] entered") w = self.param('w', make_w) print(f" [body] self.param('w') returned {w}") return w * x

Three things to name before we run it. nn.Module is the base class every Flax model inherits. @nn.compact is a decorator that permits this method to declare parameters inline; without it, declaring a parameter here is an error. self.param(name, init_fn) is the declaration itself: it takes a string name and a function that would build the array, and it calls that function with a random key.

The two print calls are ours. They are flashlights: Flax says nothing on its own, so anything printed below comes from our code.

Step 2 — run both entry points, with the prints numbered

m = Times() print("(1) calling init") p = m.init(jax.random.key(0), 3.0) print("(2) init returned:", p) print("(3) calling apply") out = m.apply(p, 3.0) print("(4) apply returned:", out)
output — real run (1) calling init [body] entered [init_fn] creating w = 2.0 [body] self.param('w') returned 2.0 (2) init returned: {'params': {'w': Array(2., dtype=float32, weak_type=True)}} (3) calling apply [body] entered [init_fn] creating w = 2.0 [body] self.param('w') returned 2.0 (4) apply returned: 6.0

Step 3 — why the initializer runs during apply, when its answer is not used

If the created value were being used, apply would ignore the dict entirely, and passing different numbers would change nothing. Test that directly:

p2 = {'params': {'w': jnp.array(5.0)}} # a dict we typed by hand print("apply with w=5.0 ->", m.apply(p2, 3.0))
output — real run [body] entered [init_fn] creating w = 2.0 [body] self.param('w') returned 5.0 apply with w=5.0 -> 15.0

There it is, in two adjacent lines. The initializer produced 2.0 and self.param returned 5.0. The created value was computed and thrown away; the returned value came out of the dict. So what was the throwaway for? Give apply a wrong shape and Flax says so itself:

class Times(nn.Module): # same module, initializer now makes shape (3,) @nn.compact def __call__(self, x): w = self.param('w', lambda key: jnp.zeros((3,))) return w * x t.apply({'params': {'w': jnp.ones((5,))}}, 2.0) # wrong shape on purpose
output — real run (URL trimmed) ScopeParamShapeError: For parameter "w" in "/", the given initializer is expected to generate shape (3,), but the existing parameter it received has shape (5,).

The initializer is run as a shape oracle. Flax asks it "what should this have looked like?", compares against what you handed in, and complains on a mismatch. Read the message closely and it describes exactly the two-mode behaviour: generated shape versus received shape.

Step 4 — the rule, and everything that follows from it

self.param(name, init_fn) in INIT mode: run init_fn, KEEP the array, file it under name self.param(name, init_fn) in APPLY mode: run init_fn for its SHAPE only, then return the array stored under name

Consequences, each of which is a thing that confuses people reading Flax for the first time:

  • Why init takes an input. The body runs for real, so shapes come from a real forward pass. That input is usually fake data of the right shape, and its values are irrelevant.
  • Why the module has no .kernel. Outside init and apply, no dict is bound, so there is nothing to return.
  • Why params come back nested. Names are filed as the body runs. A submodule's body runs inside yours, so its names nest inside yours.
  • Why you can hand-write a params dict. It is a plain dict keyed by the names you chose. Page 4 builds one by hand from NumPy arrays.

The diagram is the same body drawn twice. The only difference between the lanes is which way the arrow at self.param points: outward into a new dict, or inward from the dict you supplied.

Step 5 — the gradient, and why this design exists at all

Chapter 4's rule was that JAX differentiates a function with respect to its argument. Flax's split exists to make the parameters be that argument:

def loss_fn(params): pred = m.apply(params, 3.0) return (pred - 10.0) ** 2 print("loss :", loss_fn(p)) print("grad :", jax.grad(loss_fn)(p))
output — real run (flashlight prints from the body omitted here) loss : 16.0 grad : {'params': {'w': Array(-24., dtype=float32, weak_type=True)}}

Loss 16, gradient −24 — the same two numbers as the PyTorch autograd course, chapter 4's jax.grad demo, and the from-scratch engine in chapter 8. And notice the shape of the gradient: a dict with the same structure as the params. That is what makes the update rule a single tree operation, which page 4 uses.

Refresher: what is a pytree again, and why does grad return a dict?

A pytree is any nesting of lists, tuples and dicts whose leaves are arrays. JAX's transformations do not care about the container, only the leaves. jax.grad returns a gradient with the same container shape as its input, so differentiating with respect to a dict of 200 arrays gives a dict of 200 gradients laid out identically. Chapter 10 page 1 is the full treatment.

Where Dense_0 comes from, and the rule that breaks checkpoints

Step 1 — the class body has two kinds of names, and they behave oppositely

class Two(nn.Module): hidden: int # a FIELD — a hyperparameter scale: float = 2.0 # a FIELD with a default @nn.compact def __call__(self, x): w = self.param('w', nn.initializers.ones, (self.hidden,)) # a PARAMETER return self.scale * w * x m = Two(hidden=3) print("m.hidden (a field, readable now) :", m.hidden) try: m.w except Exception as e: print("m.w ->", type(e).__name__) print("params:", jax.tree.map(jnp.shape, m.init(jax.random.key(0), 1.0))) print("apply :", m.apply(m.init(jax.random.key(0), 1.0), 1.0))
output — real run m.hidden (a field, readable now) : 3 m.w -> AttributeError params: {'params': {'w': (3,)}} apply : [2. 2. 2.]

A Flax module is a Python dataclass, so those bare annotations at the top of the class are constructor arguments. They are settings, available immediately, and never trained. Anything created by self.param is the opposite: unavailable on the object, and trained. When you open a Flax file, sorting the class body into these two piles is the first pass.

The third argument to self.param is passed straight through to the initializer, which is how (self.hidden,) becomes the shape. Output [2. 2. 2.] is scale 2.0 times ones times x = 1.0.

Step 2 — a two-layer network, and the tree it produces

class MLP(nn.Module): hidden: int @nn.compact def __call__(self, x): x = nn.tanh(nn.Dense(self.hidden)(x)) return nn.sigmoid(nn.Dense(1)(x)) X = jnp.zeros((4, 2)) # fake batch: 4 examples, 2 features v = MLP(hidden=8).init(jax.random.key(0), X) print(jax.tree.map(jnp.shape, v))
output — real run {'params': {'Dense_0': {'bias': (8,), 'kernel': (2, 8)}, 'Dense_1': {'bias': (1,), 'kernel': (8, 1)}}}

Note the double call syntax nn.Dense(8)(x). The first pair of parentheses constructs a layer object with its settings; the second calls it on data. In torch those two steps live in different methods, __init__ and forward. Under @nn.compact they are allowed on one line, which is why Flax models look so compressed.

Step 3 — the naming rule, and the trap in it

Nobody wrote the string Dense_0. Flax generated it. The obvious guess is that it numbers layers in the order they are called. It does not: it numbers them in the order they are constructed. Two modules with identical maths, differing only in where the object is created:

class InOrder(nn.Module): @nn.compact def __call__(self, x): x = nn.Dense(8)(x) # constructed 1st, called 1st return nn.Dense(1)(x) # constructed 2nd, called 2nd class HeadFirst(nn.Module): @nn.compact def __call__(self, x): head = nn.Dense(1) # constructed 1st, called 2nd x = nn.Dense(8)(x) # constructed 2nd, called 1st return head(x) for cls in (InOrder, HeadFirst): tree = jax.tree.map(jnp.shape, cls().init(jax.random.key(0), X)['params']) print(f"{cls.__name__:10s}", {k: v['kernel'] for k, v in tree.items()})
output — real run InOrder {'Dense_0': (2, 8), 'Dense_1': (8, 1)} HeadFirst {'Dense_0': (8, 1), 'Dense_1': (2, 8)}

Read the shapes, not the names. In InOrder, Dense_0 is the 2→8 hidden layer. In HeadFirst the identical network has Dense_0 as the 8→1 output layer, because that object was constructed one line earlier. A refactor that only moves a construction line renames your checkpoint keys. Loading an old checkpoint then either errors on shape or, if the shapes happen to match, silently loads the wrong weights.

Which is why production code names layers explicitly:

x = nn.tanh(nn.Dense(self.hidden, name='fc1')(x)) return nn.sigmoid(nn.Dense(1, name='out')(x))
output — real run {'params': {'fc1': {'bias': (8,), 'kernel': (2, 8)}, 'out': {'bias': (1,), 'kernel': (8, 1)}}}

When you see name= everywhere in a Google model file, that is what it is defending against.

Step 4 — the other dialect: setup instead of @nn.compact

class MLPSetup(nn.Module): hidden: int def setup(self): # runs when the module is bound self.fc1 = nn.Dense(self.hidden) self.out = nn.Dense(1) def __call__(self, x): # no decorator here return nn.sigmoid(self.out(nn.tanh(self.fc1(x))))
output — real run {'params': {'fc1': {'bias': (8,), 'kernel': (2, 8)}, 'out': {'bias': (1,), 'kernel': (8, 1)}}}

Identical tree to the explicitly-named compact version, because here the attribute name becomes the parameter name. This shape will look familiar: it is PyTorch's layout, layers assigned in one method and used in another. The catch is that setup is still not __init__. It runs when Flax binds the module inside init or apply, not when you write MLPSetup(hidden=8), which is why m.fc1 from outside still fails.

Refresher: which one should I write, compact or setup?

Compact is the default and keeps the whole forward pass readable in one place. Reach for setup when a submodule is used in more than one method, when you need it in a non-__call__ method such as encode and decode, or when the shared submodule must be constructed once and called several times. For reading, the practical difference is only where you go to find a layer's definition.

Why real code calls apply with four arguments

The thing you will actually meet in a Google file

logits, updates = state.apply_fn( {'params': params, 'batch_stats': state.batch_stats}, batch['image'], train=True, rngs={'dropout': dropout_key}, mutable=['batch_stats'])

Five arguments and two return values, where page 1 had apply(params, x) returning one thing. Both additions come from the same source: a pure function cannot own a random seed and cannot quietly update a counter, so anything that needs either must have it passed in and handed back.

Step 1 — rngs, because dropout needs randomness it cannot generate

class WithDrop(nn.Module): @nn.compact def __call__(self, x, train: bool): x = nn.Dense(3)(x) return nn.Dropout(0.5, deterministic=not train)(x) wd = WithDrop() vd = wd.init(jax.random.key(0), jnp.ones((1,2)), train=False) print("apply(train=False) ok:", wd.apply(vd, jnp.ones((1,2)), train=False)) try: wd.apply(vd, jnp.ones((1,2)), train=True) except Exception as e: print(f"{type(e).__name__}: {e}") print("with rngs:", wd.apply(vd, jnp.ones((1,2)), train=True, rngs={'dropout': jax.random.key(1)}))
output — real run (URL trimmed) apply(train=False) ok: [[-1.7704698 1.1836556 -0.06655878]] InvalidRngError: Dropout_0 needs PRNG for "dropout" with rngs: [[-3.5409396 2.3673112 0. ]]

Three lines, three states. With train=False dropout is a no-op and no randomness is needed. With train=True and no key, Flax refuses rather than inventing a seed, and it names the collection it wants: "dropout". Given the key, it works, and you can see it working in the numbers: the third unit was zeroed, and the two survivors are exactly doubled, -1.7704698 becoming -3.5409396. That doubling is dropout's rescaling by 1/(1−0.5), so the expected value is unchanged.

The dict key matters. A layer asks for a named stream, so rngs={'params': k} would not satisfy a dropout layer. That is also why init can take a bare key: it is shorthand for {'params': key}.

Step 2 — mutable, because BatchNorm has state that is not a parameter

BatchNorm keeps a running mean and variance. They are updated every training step, but no gradient ever touches them, so they are not parameters. Flax puts them in a different collection:

class WithBN(nn.Module): @nn.compact def __call__(self, x, train: bool): x = nn.Dense(3)(x) return nn.BatchNorm(use_running_average=not train)(x) vb = WithBN().init(jax.random.key(0), jnp.ones((4,2)), train=False) print("collections:", list(vb.keys())) print(jax.tree.map(jnp.shape, vb))
output — real run collections: ['params', 'batch_stats'] {'batch_stats': {'BatchNorm_0': {'mean': (3,), 'var': (3,)}}, 'params': {'BatchNorm_0': {'bias': (3,), 'scale': (3,)}, 'Dense_0': {'bias': (3,), 'kernel': (2, 3)}}}

This is why the thing init returns is called variables and not params. It is a dict of collections, and 'params' is only one of them. The same layer appears in two collections at once: BatchNorm_0 has trainable scale and bias under params, and non-trainable mean and var under batch_stats.

Now try to train with it:

WithBN().apply(vb, jnp.ones((4,2)), train=True)
output — real run (URL trimmed) ModifyScopeVariableError: Cannot update variable "mean" in "/BatchNorm_0" because collection "batch_stats" is immutable.

Everything is frozen unless you say otherwise, so the layer's attempt to write its running mean is refused. mutable=['batch_stats'] is the permission slip, and granting it changes the return type:

y, updates = WithBN().apply(vb, jnp.ones((4,2)), train=True, mutable=['batch_stats']) print("returned two things:", type(y).__name__, list(updates.keys())) print("mean before:", vb['batch_stats']['BatchNorm_0']['mean']) print("mean after :", updates['batch_stats']['BatchNorm_0']['mean'])
output — real run returned two things: ArrayImpl ['batch_stats'] mean before: [0. 0. 0.] mean after : [-0.0177047 0.01183656 -0.00066559]

Read the last two lines against each other. The dict you passed in is unchanged, still zeros. The new numbers came back as a separate return value that you are now responsible for carrying to the next step. Nothing was mutated in place; the update was handed to you. That is the purity rule from chapter 4, showing up as an API shape.

So the five-argument call at the top of this page decodes as: here are my numbers, here is my batch, run in training mode, here is the randomness you asked for, and yes you may write to batch_stats.

The whole loop, and chapter 9's numbers to six decimals

Step 1 — prove the dict is just a dict, by writing one

Chapter 9 trained XOR in four frameworks from identical weights: 2→8 tanh, 8→1 sigmoid, MSE, plain SGD at lr 0.5. The weights came from NumPy. If a Flax params dict is really nothing but a named nesting of arrays, we can build one by hand and Flax should accept it.

rng = np.random.default_rng(0) W1 = (rng.normal(size=(2,8))*0.5).astype(np.float32); b1 = np.zeros(8, np.float32) W2 = (rng.normal(size=(8,1))*0.5).astype(np.float32); b2 = np.zeros(1, np.float32) params = {'params': {'Dense_0': {'kernel': jnp.array(W1), 'bias': jnp.array(b1)}, 'Dense_1': {'kernel': jnp.array(W2), 'bias': jnp.array(b2)}}} print("hand-built tree:", jax.tree.map(jnp.shape, params)) print("init tree :", jax.tree.map(jnp.shape, mlp.init(jax.random.key(0), Xd)))
output — real run hand-built tree: {'params': {'Dense_0': {'bias': (8,), 'kernel': (2, 8)}, 'Dense_1': {'bias': (1,), 'kernel': (8, 1)}}} init tree : {'params': {'Dense_0': {'bias': (8,), 'kernel': (2, 8)}, 'Dense_1': {'bias': (1,), 'kernel': (8, 1)}}}

The two lines are identical, so the hand-built dict is indistinguishable from the one Flax makes. The only thing init was ever doing was producing a structure we could have typed ourselves.

Step 2 — the loop, in four lines of JAX you already know

def loss_fn(p): return ((mlp.apply(p, Xd) - Yd)**2).mean() p = params for step in range(2001): l, g = jax.value_and_grad(loss_fn)(p) if step in (0,100,500,1000,2000): print(f" step {step:5d} loss {l:.6f}") p = jax.tree.map(lambda a, b: a - 0.5*b, p, g) print("preds:", np.array(mlp.apply(p, Xd)).ravel().round(3))
output — real run step 0 loss 0.251708 step 100 loss 0.177644 step 500 loss 0.004852 step 1000 loss 0.001573 step 2000 loss 0.000609 preds: [0.016 0.973 0.975 0.029]

The highlighted line is the entire optimizer. jax.tree.map with two trees walks them together, so a is each parameter array and b is its gradient, and one expression updates all four arrays at once. This works only because grad handed back a tree shaped exactly like the params, which was page 1's closing observation.

Step 3 — the same loop the way production writes it

Two pieces you will see in every real file. optax supplies optimizers as pure functions, and TrainState is a small container that carries the params, the update rule and the step count together.

import optax from flax.training import train_state state = train_state.TrainState.create( apply_fn=mlp.apply, # the module's apply, stored for later params=params['params'], # note: the INNER dict, not the variables dict tx=optax.sgd(0.5)) # same rule as the hand-written line above @jax.jit def train_step(state): def lf(pr): return ((state.apply_fn({'params': pr}, Xd) - Yd)**2).mean() l, g = jax.value_and_grad(lf)(state.params) return state.apply_gradients(grads=g), l # returns a NEW state for step in range(2001): state, l = train_step(state) if step in (0,100,500,1000,2000): print(f" step {step:5d} loss {l:.6f}")
output — real run step 0 loss 0.251708 step 100 loss 0.177644 step 500 loss 0.004852 step 1000 loss 0.001573 step 2000 loss 0.000609

Same five numbers. Three reading notes, because these trip people up:

  • params=params['params']. TrainState holds the inner dict, so the loss function has to rebuild the outer wrapper as {'params': pr}. Getting this level wrong produces a key error that reads like a missing layer.
  • state.apply_gradients returns a new state. It does not modify the old one, so state = train_step(state) is required. Dropping the assignment trains nothing and raises no error.
  • @jax.jit on the step, not the model. Chapter 4's rule: compile the largest pure function you have. The state goes in and comes out as a pytree, which is exactly what jit wants.

NNX: the same machine with the plumbing hidden

Which one will you actually open?

Flax has two APIs and you need to read both. Linen is everything on pages 0 to 4: nn.Module, init and apply, the explicit dict. NNX is the newer API, and the Flax documentation states it is going to replace linen. MaxText, Google's open reference for large language model training, migrated from linen to NNX in June 2026.

That does not make linen safe to skip. It is what a large existing corpus is written in, it is what older checkpoints and model files assume, and Flax ships a bridge specifically so the two can be mixed in one codebase. More to the point for understanding: linen shows you the mechanism that NNX hides.

Step 1 — the same layer, and the attribute that now works

from flax import nnx lin = nnx.Linear(2, 3, rngs=nnx.Rngs(0)) # in AND out, plus the key, right here print("type(lin.kernel) :", type(lin.kernel).__name__) print("lin.kernel[...] shape :", lin.kernel[...].shape) print("params live INSIDE the object:", isinstance(lin.kernel, nnx.Param))
output — real run type(lin.kernel) : Param lin.kernel[...] shape : (2, 3) params live INSIDE the object: True

Page 0's failing line now works. Three differences to register: the layer takes both dimensions, so nothing has to be discovered from an input and there is no separate init call; the random key is a constructor argument; and the array is wrapped in a Param box, which you open with [...]. In older code you will see .value for that, which still works but is deprecated.

Step 2 — the functional core is still there, one call away

If parameters live in the object, how does jax.grad differentiate with respect to them? The answer is that NNX pulls them out on demand:

graphdef, state = nnx.split(lin) print("state pure dict:", jax.tree.map(jnp.shape, nnx.to_pure_dict(state))) rebuilt = nnx.merge(graphdef, state) x = jnp.ones((1,2)) print("same output after merge:", bool(jnp.all(rebuilt(x) == lin(x))))
output — real run state pure dict: {'bias': (3,), 'kernel': (2, 3)} same output after merge: True

Read state against page 0's output. It is the same nesting of the same names with the same shapes. nnx.split gives back exactly linen's two objects: a graphdef, which is the structure and code, and a state, which is the numbers. nnx.merge puts them back together.

So nnx.jit and nnx.value_and_grad are not new kinds of transformation. Each one splits your module, calls ordinary jax.jit or jax.grad on the pure part, and merges the result back. The dict never went away. You stopped typing it.

Step 3 — same weights, same losses, third time

Load chapter 9's exact arrays into the NNX object and train it:

class NMLP(nnx.Module): def __init__(self, rngs): self.fc1 = nnx.Linear(2, 8, rngs=rngs) self.out = nnx.Linear(8, 1, rngs=rngs) def __call__(self, x): return jax.nn.sigmoid(self.out(jnp.tanh(self.fc1(x)))) nm = NMLP(nnx.Rngs(0)) print("before load, fc1.kernel[0,:3] =", np.array(nm.fc1.kernel[...][0,:3]).round(6)) nm.fc1.kernel[...] = jnp.array(W1); nm.fc1.bias[...] = jnp.array(b1) nm.out.kernel[...] = jnp.array(W2); nm.out.bias[...] = jnp.array(b2) print("after load, fc1.kernel[0,:3] =", np.array(nm.fc1.kernel[...][0,:3]).round(6)) @nnx.jit def nstep(model, opt): def lf(m): return ((m(Xd) - Yd)**2).mean() l, g = nnx.value_and_grad(lf)(model) opt.update(model, g) # mutates, torch-style return l opt = nnx.Optimizer(nm, optax.sgd(0.5), wrt=nnx.Param) for step in range(2001): l = nstep(nm, opt) if step in (0,100,500,1000,2000): print(f" step {step:5d} loss {l:.6f}")
output — real run before load, fc1.kernel[0,:3] = [ 0.75673 -0.685701 -0.568834] after load, fc1.kernel[0,:3] = [ 0.062865 -0.066052 0.320211] step 0 loss 0.251708 step 100 loss 0.177644 step 500 loss 0.004852 step 1000 loss 0.001573 step 2000 loss 0.000609

The "before" line is NNX's own initializer, which is a different scheme from chapter 9's. After the assignment the weights are chapter 9's, and the losses are chapter 9's. Two Flax dialects, four other frameworks, one set of numbers.

Two NNX-specific lines to read. opt.update(model, g) genuinely mutates the model object, which is the ergonomics chapter 3 gave up when moving to JAX. And wrt=nnx.Param tells the optimizer which boxes count as trainable, since an NNX module can also hold non-trainable state.

Step 5 — the annotation that makes Google code look alien

One more thing you will hit immediately in a real model file, and it is not in any tutorial model:

nn.Dense(8, kernel_init=nn.with_partitioning(nn.initializers.lecun_normal(), ('data', 'model')))(x)
output — real run, inspecting the resulting parameter type : Partitioned shape : (2, 8) names : ('data', 'model') unbox : ArrayImpl (2, 8)

The parameter is no longer a bare array. It is boxed in a Partitioned wrapper carrying one axis name per dimension, saying how this weight should be split across the device mesh: rows along the data axis, columns along the model axis. nn.meta.unbox takes the array back out. This is the payoff of parameters being a separate pytree. Sharding is a property you attach to the tree, and the model code never mentions devices.

Traps

  • Auto names follow construction order, not call order. Moving one line renames checkpoint keys. Pass name= in anything you will save.
  • The kernel is (in, out). Torch stores (out, in). Copying weights across without a transpose runs fine and trains badly.
  • Two levels of dict. variables holds collections; variables['params'] holds layers. TrainState stores the inner one.
  • Everything is frozen by default. A layer that wants to write state fails until you pass mutable=, and then apply returns a pair instead of a value.
  • Nothing mutates. apply_gradients returns a new state; if you drop the assignment, training silently does nothing.
  • The initializer runs during apply. It is a shape check, not a bug, and its value is discarded.
  • setup is not __init__. It runs at bind time, so attributes it defines are still unreachable from outside.

Follow-up questions, one-line answers

questionone-line answer
Why does init need an input at all?It runs your forward pass for real, and shapes like the kernel's input dimension are only knowable from a real array.
Why can't I read model.kernel?The module holds no numbers; a parameter only exists while a dict is bound, which happens inside init and apply.
What is the difference between a field and a param?Fields are dataclass annotations, readable immediately, never trained. Params come from self.param, unreadable from outside, always trained.
Why is it called variables and not params?It is a dict of collections. params is one; batch_stats is another; a model can define more.
When do I need rngs=?When a layer asks for a named random stream at call time, dropout being the usual one. Flax errors rather than inventing a seed.
Why does apply sometimes return two things?Because you passed mutable=. The updated collections come back as a second value for you to carry forward.
Is NNX a different framework?No. nnx.split produces linen's exact structure; the transformations split, call plain JAX, and merge back.
Which should I learn to read first?Both, and linen first, because it makes the parameter tree visible instead of hiding it.
What are those axis-name tuples in model files?nn.with_partitioning boxes a parameter with one mesh axis name per dimension, so sharding is attached to the tree rather than the code.

Where it came from

Flax began at Google Brain in 2020 as a rewrite of an earlier JAX network library, with linen as its second-generation API. DeepMind maintained a competing library, Haiku, until July 2023, when it entered maintenance mode and DeepMind recommended Flax for new projects, citing a broader feature set and more adoption outside Alphabet. NNX was designed to answer linen's main complaint, that the functional style is hard to learn and hard to debug, by putting parameters back inside module objects while keeping the functional core reachable through split and merge. Flax's documentation now describes NNX as the API that will replace linen, and MaxText completed its migration in June 2026.
