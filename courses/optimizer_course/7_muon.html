Muon — stop treating the matrix as a bag of scalars

Chapter 7. Six chapters of optimizers, and every one of them looks at a weight matrix and sees only its individual entries. This chapter is what becomes visible when you look at the matrix — and the first optimizer since Adam to win real LLM pretraining races.

Start with the standalone story: Muon, one step at a time →

What every previous chapter had in common — and couldn't see

Elementwise, all the way down

Write any update from chapters 1–6 for a weight matrix W and the honest notation is:

for every entry (i,j) INDEPENDENTLY: W[i,j] ← W[i,j] − lr · step(g[i,j], its own history)

Adam keeps two numbers per entry; LaProp reorders a division per entry; none of them ever asks how entry (0,1) relates to entry (2,3). The matrix is treated as a bag of unrelated scalars that happen to be stored in a grid.

But the grid is not storage — it's a function: W maps an input vector to an output vector, y = W·x. Functions have properties no single entry owns: which input directions get amplified, which get ignored. The claim of this chapter: gradient updates for W have extreme, invisible structure at that level — and fixing it is worth ~2× in compute.

The plan, so nothing arrives unannounced

  • Page 1: see the structure — a real gradient matrix is nearly rank-1, and momentum makes it worse.
  • Page 2: state the wish, which is chapter 3's wish one level up — equalize per direction, not per entry.
  • Page 3: the trick that grants it without an SVD — Newton–Schulz, five matmuls.
  • Pages 4–5: the assembled optimizer, its exclusions and costs, and the production receipts.

A weight-matrix gradient is a stack of outer products — and it's lopsided

Step 1a — one single entry, by the chain rule

Before any matrix talk: what is the gradient of one weight? Take a linear layer y = W·x with W of shape 3×4 (3 outputs, 4 inputs). Write out one output:

y[0] = W[0,0]·x[0] + W[0,1]·x[1] + W[0,2]·x[2] + W[0,3]·x[3]

Now ask for ∂L/∂W[0,1]. Two factors, and that's all:

∂y[0] / ∂W[0,1] = x[1] # W[0,1] multiplies x[1] and appears nowhere else ∂L / ∂y[0] = e[0] # this IS what "the error signal at output 0" means chain rule: ∂L/∂W[i,j] = e[i] · x[j] # an output's error times the input it multiplied

With x = [1.0, 0.5, −0.3, 0.8] and e = [2.0, −1.0, 0.5]: ∂L/∂W[0,1] = 2.0 × 0.5 = 1.0. Nothing matrix-shaped has happened yet — this is one number.

Step 1b — do that for all 12 entries and a multiplication table appears

The rule e[i]·x[j] has to be evaluated for every (i,j). Lay it out as a grid, rows labelled by e, columns by x:

output — real run x= 1.0 0.5 -0.3 0.8 e = 2.0 2.000 1.000 -0.600 1.600 e = -1.0 -1.000 -0.500 0.300 -0.800 e = 0.5 0.500 0.250 -0.150 0.400

That grid — every entry of one vector times every entry of another — is exactly what the outer product e·xᵀ means. It is not a new operation to learn; it is the multiplication table you just built, given a name. So for one training example:

grad W (from one example) = e · xᵀ # shape (3×1)(1×4) = 3×4, same shape as W ✓

Step 1c — look at that grid again: every row is the SAME vector, rescaled

This is the step everything later depends on, so read the rows, not the entries:

output — real run row 0 = [ 2.00 1.00 -0.60 1.60] = 2.0 × x row 1 = [-1.00 -0.50 0.30 -0.80] = -1.0 × x row 2 = [ 0.50 0.25 -0.15 0.40] = 0.5 × x divide row-by-row and the ratio is CONSTANT along each row: row1/row0 = [-0.5 -0.5 -0.5 -0.5] row2/row0 = [0.25 0.25 0.25 0.25]

Of course they are — row i is e[i]·xᵀ, so the only thing that changes from row to row is the scalar e[i]. Every row points along x; only the loudness differs.

A matrix whose rows are all multiples of one vector has exactly one independent direction. That property has a name — rank 1 — and one way to detect it is that all but one singular value is zero:

output — real run rank(e·xᵀ) = 1 singular values = [3.2241, 0.0000, 0.0000]

Read that as a statement about the update: one training example can only ever push W along a single direction. It has seen one input; it has no opinion about any other.

Step 1d — a batch: gradients ADD, so the sheets stack

Why do examples combine by addition? Because the batch loss is a sum over examples, and differentiation is linear — the derivative of a sum is the sum of the derivatives. Nothing deeper:

L = L₁ + L₂ + … ⇒ grad W = e₁·x₁ᵀ + e₂·x₂ᵀ + … # one rank-1 sheet per example

Take two examples — two similar tokens, since real text is full of those:

output — real run x₁=[1.0, 0.5, -0.3, 0.8] e₁=[2.0, -1.0, 0.5] x₂=[0.7, 0.9, 0.1, 0.5] e₂=[1.5, -0.2, 1.0] e₁x₁ᵀ = [[ 2.00 1.00 -0.60 1.60] e₂x₂ᵀ = [[ 1.05 1.35 0.15 0.75] [-1.00 -0.50 0.30 -0.80] [-0.14 -0.18 -0.02 -0.10] [ 0.50 0.25 -0.15 0.40]] [ 0.70 0.90 0.10 0.50]] G = sum = [[ 3.05 2.35 -0.45 2.35] [-1.14 -0.68 0.28 -0.90] [ 1.20 1.15 -0.05 0.90]]

Now redo step 1c's row reading on the sum. Each row is no longer a multiple of one vector — it is a combination of two:

output — real run row 0 of G = 2.0·x₁ + 1.5·x₂ = [ 3.05 2.35 -0.45 2.35] row 1 of G = -1.0·x₁ + -0.2·x₂ = [-1.14 -0.68 0.28 -0.90] row 2 of G = 0.5·x₁ + 1.0·x₂ = [ 1.20 1.15 -0.05 0.90] check row 0 by hand: 2.0·[1.0,0.5,-0.3,0.8] + 1.5·[0.7,0.9,0.1,0.5] = [3.05, 2.35, -0.45, 2.35] ✓

Every row of G lives inside the 2-D plane spanned by x₁ and x₂ — a plane sitting inside 4-D input space. So G has rank 2, no matter that it has 12 entries and 4 columns, and the general statement follows: a gradient matrix cannot contain more independent directions than the number of distinct examples that built it. Batch of 32 into a 4096×4096 weight? Rank at most 32.

Step 2 — measuring the directions, and where the rank shows up

"Rank" is a yes/no count — a direction is either present or absent. What we actually need is how strongly each direction is pushed, and that is exactly what the SVD reports. Any matrix factors as G = U·S·Vᵀ: Vᵀ picks out input directions, S scales them, U places them in output space. The entries of S are the singular values — the strength along each principal direction.

output — real run singular values of G: [5.1644, 0.3234, 0.0000] s₁/s₂ = 16.0

Check it against step 1d before reading on: the third value is 0.0000 — that zero IS the rank-2 fact. Two examples built G, so at most two directions can be nonzero, and the count of nonzero singular values is precisely the rank. The SVD didn't add information; it graded the directions we already knew were there.

Now the part that matters: those two nonzero values are 16× apart. Update W with this G and you shove hard along one axis of the function and barely graze the second. And it isn't arbitrary — the lopsidedness is caused by the tokens being similar:

output — real run: same e's, different second input cos(x₁, x₂) = 0.865 (30° apart, "similar tokens") → svs [5.164, 0.323] s₁/s₂ = 16.0 cos(x₁, x') = 0.156 (nearly perpendicular) → svs [3.853, 0.683] s₁/s₂ = 5.6

When two inputs point the same way, their sheets reinforce along the shared direction and only their small difference survives elsewhere — so one singular value swells and the other shrinks. Real token streams are overwhelmingly of the first kind. Overlapping data is what manufactures a lopsided update.

Refresher: SVD in sixty seconds, on this exact matrix

Any matrix does three things in a row: rotate the input (Vᵀ), stretch along perpendicular axes (S), rotate into output space (U). Feed G the input direction v₁ (first column of V) and out comes u₁ scaled by 5.164; feed it v₂ and out comes u₂ scaled by 0.323; feed it anything perpendicular to both and out comes ~0. Those are the only things G can do. "Nearly rank-1" means one singular value dwarfs the rest without the others being exactly zero — and step 3 below drives s₁/s₂ from 16 to 69.

Step 3 — momentum makes it worse, and you can watch it happen

Chapter 2's lesson: consistent directions accumulate in the buffer, fluctuating ones cancel. Across a stream of batches the shared direction is the consistent one, so momentum should concentrate the matrix further onto it. Run it — buffer M ← 0.95·M + e·xᵀ, where each step draws e = e₁ + 0.3·𝒩(0,1) and x = x₁ + 0.3·𝒩(0,1), i.e. the same underlying signal with noise on top:

output — real run: numpy default_rng(1), 50 steps t= 1: svs = [ 2.739, 0.000, 0.000] s₁/s₂ = — # one sheet, rank 1 t= 5: svs = [11.693, 0.296, 0.073] s₁/s₂ = 39.6 t=10: svs = [23.658, 0.622, 0.090] s₁/s₂ = 38.0 t=25: svs = [42.203, 0.413, 0.088] s₁/s₂ = 102.2 t=50: svs = [56.719, 0.822, 0.138] s₁/s₂ = 69.0, s₁/s₃ = 411

Read the columns separately — that is where the mechanism is visible. s₁ grows from 2.7 to 56.7 (×21) while s₂ stays around 0.5–0.8 and s₃ never leaves the noise floor. The signal direction compounds because it repeats; the others get re-randomized each step and cancel, exactly as chapter 2 described — only now you can see it happen to a spectrum rather than to a single number.

This is the observation the Muon write-up reports for real transformers: SGD-momentum and Adam updates for 2-D weights "have very high condition number — almost low-rank… dominated by just a few directions." The quiet directions aren't absent — they are 69× to 411× too quiet to matter. It is the matrix-level version of chapter 3's cold embedding row: the signal is present, the scale is wrong.

Equalize per direction — the exact analogy to chapter 3

Same wish, new granularity

Dividing each direction by its own strength means: replace every nonzero singular value by 1, keeping the directions. Watch what that does to the factorization — S becomes the identity, and an identity sitting in the middle of a product simply vanishes:

M = U·S·Vᵀ # S = diag(56.72, 0.82, 0.14) set every nonzero sᵢ → 1: O = U·I·Vᵀ = U·Vᵀ # there is nothing left to multiply by

That is the whole content of "orthogonalize": keep both rotations, delete the stretch between them. And the name is earned — a matrix whose singular values are all 1 has orthonormal rows (or columns, whichever side is shorter), which follows in one line from U and V having orthonormal columns:

output — real run: M is 3×4, so it is the rows that are orthonormal (U·Vᵀ)(U·Vᵀ)ᵀ = U VᵀV Uᵀ = U·I·Uᵀ = I # VᵀV = I, then UᵀU = I singular values of U·Vᵀ: [1.0, 1.0, 1.0]

U·Vᵀ is also the closest such matrix to M — closest in the ordinary Frobenius (sum of squared entries) sense. So this is not an invented update: it is M snapped to the nearest matrix whose directions all carry equal weight. The 69× whisper and the shout now push with the same force; the whisper was real signal — it took 50 steps of consistent gradients to build — it was just drowned.

Why not just run an SVD every step?

Because you'd run one per weight matrix per step, in fp32 (SVD is numerically delicate), on the training critical path. The entire practical content of Muon is a cheaper route: a fixed polynomial, applied five times, that sands every singular value toward 1 without ever computing what the singular values are. That trick is the next page — and it's the reason the method is called Momentum Orthogonalized by Newton–Schulz.

Deeper "why": in what sense is UVᵀ the right update? (steepest descent under a different ruler)

SGD's step is "steepest descent if step length is measured entry-wise" (Euclidean). Measure step length by the spectral norm instead — how much the matrix can stretch any single input — and the steepest-descent direction for a linear loss becomes exactly UVᵀ of the gradient. Since what a layer does to activations is bounded by its spectral behavior, that ruler matches the function, not the storage. Same pattern as ever: every optimizer is steepest descent under some norm; the norm is the design choice.

Newton–Schulz: sandpaper that only touches singular values

Step 1 — the enabling fact, verified not asserted

Take an odd polynomial in matrix form: p(X) = a·X + b·(XXᵀ)X + c·(XXᵀ)²X. Substitute X = U·S·Vᵀ and push it through one factor at a time. The only fact used is that U and V have orthonormal columns, so UᵀU = I and VᵀV = I:

XXᵀ = (USVᵀ)(USVᵀ)ᵀ = USVᵀVSUᵀ = U S² Uᵀ # V cancels itself (XXᵀ)X = (US²Uᵀ)(USVᵀ) = US²UᵀUSVᵀ = U S³ Vᵀ # now U cancels itself (XXᵀ)²X = … the same trick once more … = U S⁵ Vᵀ so p(USVᵀ) = U·(aS + bS³ + cS⁵)·Vᵀ = U · φ(S) · Vᵀ # same U, same V, only S reshaped

And now you can see why it has to be odd. Each XXᵀ contributes an S² but leaves a trailing Uᵀ behind; only a final X — which carries the Vᵀ — sends the result back into the right space. An even term such as XXᵀ on its own would give U S² Uᵀ, which for our 3×4 matrix is 3×3: the wrong shape to add to X at all. Odd powers land back where X lives; even ones do not.

Since S is diagonal, φ(S) just means "apply the scalar function φ(s) = 3.4445s − 4.7750s³ + 2.0315s⁵ to each singular value separately." That is a matrix identity, so test it — on page 1's own G, Frobenius-normalized:

output — real run singular values of X: [0.9980, 0.0625, 0.0000] φ(s) applied to each number: [0.7024, 0.2141, 0.0000] singular values of p(X): [0.7024, 0.2141, 0.0000] match = True

So the matrix expression — three matmuls, no decomposition anywhere — is the scalar function φ applied to every singular value at once, blind to what those values are. Note the quiet one: 0.0625 → 0.2141, an amplification of ×3.43. That is no coincidence — near zero φ(s) ≈ 3.4445·s, and 3.4445 is exactly the coefficient a. The polynomial is a steep amplifier precisely where the drowned directions live.

Step 2 — iterate the scalar curve and watch everything herd toward 1

Two things happen before the iteration runs. First Frobenius-normalize — divide by √(sum of squared entries). That guarantees every singular value lands in (0, 1], and the reason is a one-liner worth keeping: the Frobenius norm squared is the sum of the squared singular values, so no single one can exceed it.

‖X‖₂F = ∑ᵢ sᵢ² ≥ s₁² ⇒ s₁ ≤ ‖X‖F ⇒ after dividing by ‖X‖F, every sᵢ ≤ 1 check on our X: ∑sᵢ² = 1.000000 ≥ s₁² = 0.996095 ✓ (s₁ = 0.9980)

That matters because φ is only well-behaved on (0, 1] — feed it a singular value of 56 and the s⁵ term explodes. Normalization is what makes a fixed polynomial safe for any input matrix. Then apply φ five times:

output — real run: 5 iterations of φ from different starting values s₀=0.05: 0.050 → 0.172 → 0.567 → 1.202 → 0.944 → 0.758 s₀=0.20: 0.200 → 0.651 → 1.162 → 0.815 → 0.953 → 0.747 s₀=0.50: 0.500 → 1.189 → 0.896 → 0.824 → 0.938 → 0.765 s₀=1.00: 1.000 → 0.701 → 1.114 → 0.721 → 1.090 → 0.696

Values 20× apart all end in a band around ~0.7–1.1. Not exactly 1 — the iteration oscillates there rather than converging (φ(1) = 0.701, not 1). That's a deliberate trade: these coefficients were themselves tuned by gradient descent to maximize steepness at 0 — rescue the drowned directions fast — at the price of never settling exactly. "All singular values ≈ 1 ± 0.3" turns out to train just as well as exactly 1, and the steep-at-0 property is what 5 iterations buys.

Step 3 — the real thing: NS5 on the page-1 momentum matrix

output — real run: O = NewtonSchulz₅(M) singular values of M: [56.72, 0.82, 0.14] ratios 1 : 0.014 : 0.002 singular values of O: [ 0.99, 0.94, 0.70] ratios 1 : 0.96 : 0.71 Uᵀ·O·V = [[0.697 −0.000 −0.000] # diagonal in M's OWN singular basis: [−0.000 0.944 −0.000] # directions preserved EXACTLY, [−0.000 0.000 0.987]] # strengths equalized 500:1 → 1.4:1

Read the middle block first, because it is the whole chapter in one printout. Sandwiching O between M's own singular vectors asks a precise question: does O act along the same axes M did? If O had rotated anything, off-diagonal entries would appear. They are all −0.000. So O pushes along exactly M's directions — nothing rotated, nothing invented; only the numbers on the diagonal changed, from 56.72 / 0.82 / 0.14 to 0.99 / 0.94 / 0.70. The direction that was 411× too quiet now contributes to the step about as loudly as the dominant one.

(The diagonal reads 0.697, 0.944, 0.987 while the sorted singular values read 0.99, 0.94, 0.70 — same three numbers. The diagonal is in M's original strength order, the singular-value list is sorted descending; φ is not monotonic on (0,1], so it can reorder them. Harmless here, since the target is "all ≈ 1" either way.)

The actual code (5 lines of matmuls) and why bf16 is enough
def newtonschulz5(G, steps=5, eps=1e-7): a, b, c = (3.4445, -4.7750, 2.0315) X = G.bfloat16(); X /= (X.norm() + eps) # Frobenius-normalize → all σ ≤ 1 if G.size(0) > G.size(1): X = X.T # work on the short side (cheaper XXᵀ) for _ in range(steps): A = X @ X.T X = a*X + (b*A + c*A@A) @ X return X.T if G.size(0) > G.size(1) else X

Because the target is "everything ≈ 1, roughly," precision barely matters — the iteration is self-correcting within its band, so bf16 works where classical exact-orthogonalization iterations demand fp32. That's what makes it cheap enough for the training loop.

Muon assembled — and the fine print that makes it deployable

The whole update

M ← μ·M + grad # ch. 2's buffer, per weight MATRIX (μ ≈ 0.95, Nesterov flavor) O ← NewtonSchulz₅(M) # equalize its directions (previous page) W ← W − lr · O # step along every direction with equal force

Note what's gone relative to Adam: no v, no ε, no bias correction — one buffer per matrix instead of two per scalar, and the normalization is geometric, not statistical. Chapter 3's wish is granted by a different mechanism entirely: not "divide by your typical size" but "flatten the spectrum."

Where Muon must NOT be used — and the reason is the chapter's own logic

parametersoptimizerwhy
hidden-layer weight matrices (attention proj., MLPs)Muonthey're linear maps; directions are the right unit
embedding tableAdamWits input is a one-hot, not a dense activation — which breaks the assumption Muon is derived from. Next card.
final head / output layerAdamWsame family of reason (its output is logits, not a dense activation) — but see the honesty note: I'm less sure about this one than the embedding
gains, biases, norms (1-D)AdamWno matrix, nothing to orthogonalize

So real "Muon training" is always a hybrid: Muon for the interior, AdamW for the edges — the course's chapters 1–6 don't retire, they get a smaller kingdom.

"Why not embeddings — is it because they're sparse?" — the answer is no, and the real reason is better

Sparsity is the natural guess: in any batch, most rows of a 151,936-row embedding table get exactly zero gradient, so it's tempting to say orthogonalization can't cope. Test it, and that story dies. Feed Newton–Schulz a matrix with mostly-zero rows:

output — real run: 12 "tokens", only rows 1, 4, 7 active row norms of G : [0 0.674 0 0 1.736 0 0 1.577 0 0 0 0] row norms of NS5(G) : [0 0.911 0 0 1.000 0 0 0.843 0 0 0 0] zero rows preserved exactly? True

And it's not luck — it's forced by the algebra. Every term of the iteration ends in X, and A = XXᵀ has a zero row wherever X does, so a token that got no gradient gets no update. Sparsity, in the "many empty rows" sense, passes through Muon untouched.

The actual reason is what the update is measured in. Page 2's foldable said every optimizer is steepest descent under some norm, and the norm is the design choice. Muon is steepest descent under the RMS→RMS operator norm — and that derivation assumes the layer maps a dense activation vector to another one. Jeremy Bernstein, deriving Muon, says so directly: a Linear layer assumes "the vectors x and y are 'dense' activation vectors, meaning the entries are close to unit size," and that assumption is what "separates the Linear layer from, say, an Embedding layer that takes one-hot inputs."

An embedding's input is not dense — it is one-hot. Change the input geometry and the correct norm changes with it: for one-hot in, dense out, the natural choice is the ℓ₁→ℓ₂ operator norm (this is what Bernstein's modula library implements for embedding layers). And that norm is a completely different object — because the maximum of a convex function over the ℓ₁ ball is attained at a vertex, and a vertex of the ℓ₁ ball is a one-hot, i.e. a single token:

output — real run: V=5 tokens, d=3 best over 400,000 random interior points : 2.407735 best at a VERTEX (a one-hot) : 2.646872 <- the true ℓ₁→ℓ₂ norm = max over tokens of that token's row norm

So the two duality maps ask for different things, and neither implies the other:

hidden linear layer → RMS→RMS → set every SINGULAR VALUE to 1 # Muon / UVᵀ embedding table → ℓ₁→ℓ₂ → set every TOKEN'S ROW NORM to 1

And Muon does not deliver the second. On a Zipfian embedding gradient (V=2,000, d=64) — after orthogonalization:

output — real run row-norm spread (max/min) after Muon : 96.8× # the ℓ₁→ℓ₂ target is 1.0x col-norm spread (max/min) after Muon : 1.16× # it equalized the d DIRECTIONS instead

For V ≫ d those are very different requests: Muon equalizes the d column directions, while what an embedding table needs equalized is its V token rows. The mismatch isn't sparsity — it's that Muon is normalizing the wrong axis for this layer.

Independent corroboration that this axis is real: Muown (Lion et al., May 2026) identifies uncontrolled row-norm growth as the empirical driver of Muon's spectral-norm drift — a live pathology even in the hidden layers Muon is designed for, which they fix by promoting row magnitudes to an explicit optimizer variable. In an embedding table, rows aren't an internal detail; each one is a token.

The bill: under 1% extra FLOPs — check it yourself

NS runs on the momentum matrix once per step: for a square m×m weight that's ~T·(4m³)-ish matmul work against a forward+backward that already costs ~6·m²·B for batch of B tokens — the write-up's bound is overhead ≤ T·m/B:

output — real run of the formula nanoGPT speedrun m=768, B=524,288: 5·768/524288 = 0.73% Llama-405B scale m=16,384, B=16,000,000: 5·16384/16000000 = 0.51%

Memory: one buffer per matrix — half of Adam's state. Recall chapter 4's bill (2 floats/param, 56 GB for 7B): Muon's interior costs 1 float/param.

Scaling patches (Moonshot, "Muon is Scalable for LLM Training"): decay + one derivable constant

Two changes took Muon from speedruns to a 5.7-trillion-token production model. First, standard AdamW-style weight decay (at that horizon, unregularized weights drift). Second — and this one you can derive — match the update's RMS to what AdamW produces, so one lr works for both halves of the hybrid. An orthogonalized m×n matrix has min(m,n) singular values ≈ 1, so its entry-RMS is fixed by shape alone:

output — real run: RMS of UVᵀ for random matrices 1024×1024: RMS = 0.03125 = 1/√1024 4096×1024: RMS = 0.01562 = 1/√4096 768×3072: RMS = 0.01804 = 1/√3072 pattern: RMS(UVᵀ) = 1/√max(m,n) exactly

AdamW's typical update RMS in practice is around 0.2 — note that this one number is an empirical constant from the Moonshot report, not something derived here; everything else in this card is. So multiply Muon's update by 0.2·√max(m,n) and every parameter in the network — Muon-run or AdamW-run — moves on the same scale, under one lr and one schedule. A hyperparameter eliminated by geometry.

The receipts — and what the whole course looks like from here

Public numbers, attributed

  • NanoGPT speedrun (Keller Jordan, Oct 2024): Muon improved training speed ~35% on the record attempt, and stayed the optimizer of choice through all 12 subsequent records set by 7 different researchers. CIFAR-10 speedrun: 3.3 → 2.6 A100-seconds.
  • Moonlight (Moonshot AI, Feb 2025): 16B-MoE trained 5.7T tokens on Muon; scaling-law sweeps report ≈ 2× compute efficiency vs AdamW at compute-optimal settings.
  • Kimi K2 (2025): a 1-trillion-parameter production model trained with MuonClip — Muon plus a query-key logit clip for attention stability. The first frontier-scale model whose optimizer is not an Adam descendant.

Honest caveat, same voice as chapter 4's: on small clean problems tuned AdamW still matches it; the wins concentrate where the update-spectrum disease actually bites — large transformer interiors, long horizons.

Follow-up questions worth being able to answer

questionone-line answer
Why does orthogonalizing help at all?Real 2-D updates are near-rank-1 (we measured s₁/s₂ = 69 after momentum); UVᵀ restores the drowned-but-consistent directions to full volume.
Why Newton–Schulz instead of SVD?An odd matrix polynomial provably acts on singular values only; 5 bf16 matmul rounds ≈ UVᵀ at <1% FLOP overhead, no fragile decomposition on the training path.
Why not on embeddings — is it the sparsity?No. Newton–Schulz preserves zero rows exactly (every term ends in X). The reason is the norm: Muon is steepest descent under RMS→RMS, which assumes dense inputs; an embedding takes a one-hot, whose natural ℓ₁→ℓ₂ duality map equalizes each token's row norm — a different axis than Muon's singular values (measured: 96.8× row spread left over).
Is that the settled explanation?The practice is universal and stated in the release; the norm argument is the accepted reasoning; I could not find a clean published ablation isolating the mechanism, and the output-head case is less clearly pinned down than the embedding case. See the honesty note on tab 4.
Why is it cheaper in memory than Adam?One momentum buffer per matrix; no v, no ε, no bias correction — half of Adam's optimizer state.
Does the iteration converge to exactly 1?No — it oscillates in ~[0.7, 1.1] by design; coefficients trade exact convergence for steepness near 0, which is where the drowned directions live.
Is Muon "adaptive" in the ch. 3 sense?Yes in spirit, no in mechanism: same equalize-the-loud-and-quiet plot, but via spectrum geometry instead of a running statistical estimate.
