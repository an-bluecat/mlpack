Chapter 16: The Training Layout

Every chapter so far described a loss. This one describes the machine: which models are resident for PPO vs GRPO vs distillation, which GPUs generate, which train, and why "just use the same GPUs for both" is the right default until suddenly it isn't.

Why This Is a Real Problem: Two Jobs That Both Want All the Memory

The loop, and the two hats one model has to wear

Every method from chapter 5 onward has the same shape:

1. GENERATE sample responses from the current policy // inference job
2. SCORE verifier, reward model, or teacher
3. UPDATE backward + optimizer step // training job
4. repeat — and step 1 must use the UPDATED weights

Steps 1 and 3 use the same model but want completely different things from a GPU. That conflict is this whole chapter.

Count the bytes — training state first

An 8B model under mixed-precision AdamW. Per parameter:

whatbytes/paramfor 8B
bf16 weights214.9 GB
fp32 master copy429.8 GB
Adam m (fp32)429.8 GB
Adam v (fp32)429.8 GB
bf16 gradient214.9 GB
total16119 GB

Note the ratio hiding in that table: training costs 16 bytes/param, inference costs 2 — an 8× difference. A model you can serve on one GPU may need eight to train.

Now count the KV cache — and this is the number that decides the architecture

To generate, the inference engine caches keys and values for every token of every in-flight sequence. Llama-3-8B geometry (32 layers, 8 KV heads with GQA, head_dim 128, bf16):

per token = 2 (K,V) × 32 layers × 8 heads × 128 dim × 2 bytes
= 131,072 bytes = 128 KB per token
 
a 2,048-token sequence → 0.25 GB
a 20,480-token sequence → 2.50 GB // DAPO's cap, ch. 15

Now put it against the training state, for a realistic batch (256 sequences, as in ch. 11) on a full node of 8×H100 80GB = 640 GB of HBM:

whatmemoryfits in 640 GB alongside training?
training state (8B, AdamW)119 GByes — 15 GB per GPU sharded
KV for 32 seqs @ 2,048 tok8 GBcomfortably
KV for 256 seqs @ 20,480 tok640 GBno — that is the entire node, by itself

Read the last row. At long-reasoning lengths the KV cache is five times larger than the whole training state. It is not a rounding error competing with optimizer memory — it is the dominant consumer. Everything in this chapter follows from that one inequality.

So there are exactly three things you can trade

(a) SHARE the GPUs and time-slice → tab 2, "colocated"
(b) SPLIT the GPUs into two pools → tab 3, "disaggregated"
(c) SHRINK the batch or the length → always available, always painful

And your instinct that you might just use the trainer GPUs to generate is not only valid — it is the standard default. Tab 2 is that design — but first, tab 1 counts how many models are even in the room, because that number differs a lot between PPO, GRPO and distillation.

Which Models Are Actually in the Room

Before asking which GPU does what, ask how many models there are

"The policy" is never the only thing resident. Each algorithm needs a different cast, and each member is either trained (16 bytes/param — weights, fp32 master, Adam m and v, gradient) or frozen (2 bytes/param — bf16 weights, forward passes only). At 8B per model:

algorithmmodels residenttotal
PPO / RLHF (ch. 5)policy T + critic T + reward model F + reference F268 GB
GRPO (ch. 7)policy T + reference F  (verifier is code, not a model)134 GB
DAPO (ch. 15)policy T  (KL deleted, so no reference)119 GB
on-policy distillation (ch. 11)student T + teacher F134 GB

Read it as a progression and the whole arc of Part 2 falls out:

PPO → GRPO : delete the CRITIC → saves 119 GB (44% of PPO's total)
GRPO → DAPO : delete the REFERENCE → saves 15 GB + a whole forward pass per step
 
PPO → DAPO overall: 2.2× less model memory

Chapter 7 tells you GRPO drops the critic because a group mean is a cheaper baseline than a learned value function. This table is why that mattered enough to name an algorithm after: the critic is a second trained model, so deleting it removes more memory than the reward model and reference combined.

The one that surprises people: the verifier is not a model

// RLHF's grader — a neural network, needs a GPU:
reward = RM(prompt, response) // 15 GB resident, forward pass per response
 
// GRPO/DAPO's grader — ordinary code, runs on CPU:
def reward(response, answer):
return 1.0 if extract_number(response) == answer else 0.0
// 0 GB. 0 GPU time.

So "verifiable rewards" is not only an argument about reward hacking (ch. 15 tab 5) — it is also a systems win. You delete a model from the room and replace it with a function call.

Colocated: The Same GPUs Do Both, In Turns

The design

One pool of GPUs holds everything and alternates roles. This is verl’s HybridEngine, and it is what most open-source RL post-training runs on.

// ---- generation phase ----
free the gradient buffers
offload optimizer state (Adam m, v) to CPU RAM
hand the freed HBM to the inference engine's KV cache
generate 256 sequences
 
// ---- training phase ----
tell the engine to release its KV cache // vLLM calls this "sleep"
bring the optimizer state back from CPU
forward, backward, step
 
// ---- repeat ----

The two phases are strictly serialized: while generating, nothing trains; while training, nothing generates.

Why this is the sensible default

advantagewhy it matters
Weight sync is nearly freeThe updated weights are already on the device the generator will use. No network transfer — a local reshard at worst. Compare tab 2, where you broadcast billions of parameters every sync.
Strictly on-policy for freeGeneration cannot start until the update finishes, so the data always comes from the current weights. No staleness to correct.
No idle poolEvery GPU is doing the one thing that is happening. In a split layout, whichever pool is not the bottleneck is partly idle.
Much simplerOne resource pool, one process group, no queue between two clusters, no separate failure domains.

What it costs you

  • No overlap. Generation is usually the long pole; during it, all your expensive training capacity is doing inference work it is over-provisioned for.
  • The KV cache is squeezed. Even with the optimizer offloaded, the weights and activations stay resident, so the engine gets a fraction of HBM. In verl this is literally a knob — vllm_gpu_memory_utilization, dropped from ~0.90 to ~0.80 when sharing — and a smaller KV budget means fewer concurrent sequences, which means slower generation.
  • Offload traffic. Shuttling ~60 GB of Adam state to CPU and back every iteration is not free.

Notice the vicious bit: colocating makes generation slower exactly when generation is already the bottleneck, because it is the KV budget you took away.

Disaggregated: Two Pools, and Now Time Runs in Parallel

The design

GENERATOR pool student weights, bf16 only // 15 GB for 8B
no gradients, no optimizer state
→ ALL remaining HBM goes to KV cache
runs vLLM / SGLang
 
TRAINER pool weights + gradients + optimizer // 119 GB for 8B
sharded (FSDP / ZeRO)
 
// they run AT THE SAME TIME, connected by a queue:
generator ——rollouts——> [queue] ——> trainer
generator <——new weights———————— trainer

The reason to do this is on tab 0: give the KV cache the full VRAM budget of its own node instead of the leftovers. Generation throughput rises, and you can scale the two pools independently — more generator replicas if generation dominates, a bigger training mesh if it does not.

But you have just bought a staleness problem

Overlap is the point, and overlap is exactly what breaks on-policyness. If the generator is producing while the trainer is stepping, then by the time a rollout is consumed the weights have moved:

rollout produced by θt
consumed to update θt+k // k = how far the pools have drifted
 
k = 0 → strictly on-policy, but no overlap (that's tab 1)
k = 1 → one step stale; usually fine
k large → the ratio in ch. 5's loss is doing heavy lifting, and
eventually the clip is active on everything and learning stalls

So k is the real design dial, and chapter 9’s on/off-policy spectrum is the theory for it. The importance ratio and clip you learned in chapter 5 are precisely what make k > 0 survivable at all.

And weight sync is now a real line item

8B model, bf16 weights = 15 GB to push to every generator replica,
every time you want them refreshed.
 
// Hence the temptation, and the trap:
sync less often → cheaper → but k grows → more staleness

This is the trade in one line: you are exchanging on-policyness for GPU utilization, and the exchange rate is how often you can afford to broadcast weights.

Choosing between the two

colocateddisaggregated
KV cache budgetleftoversthe whole node
overlapnoneyes
weight synclocal, ~freenetwork broadcast
stalenessnonek > 0, must be managed
complexitylowhigh
use it whenshort-to-medium responses; one node; you want simple and correctlong reasoning traces; many nodes; generation clearly dominates wall-clock

The honest summary of what people do: start colocated. Move to disaggregated when the profile says generation is eating your run and the KV squeeze is why.

Where the Teacher Sits (and Why It Is the Easy One)

A third pool is usually unnecessary

For on-policy distillation (ch. 11) there is a third model. It sounds like a third pool. It usually is not, because of what the teacher does not need:

roleneedsbytes/param8B model
student (training)weights + grads + Adam16119 GB
student (generating)weights + KV cache2 + KV15 GB + KV
teacher (scoring)weights only215 GB

The teacher never generates, never backprops, and holds no optimizer state. It also does exactly one forward pass per batch, over text that already exists. So it is cheap in both memory and time, and it typically just co-resides with the trainer.

The phase diagram for distillation

// colocated variant — the common case
phase 1 STUDENT generates → KV cache active, optimizer offloaded
phase 2 TEACHER scores → one forward pass over the student's text
phase 3 STUDENT updates → KV released, optimizer resident
 
// Note phase 2 is short. The teacher is not the bottleneck —
// phase 1 is, as always.

One thing worth knowing: since the teacher is larger than the student, its 2 bytes/param can still be the biggest single weight tensor in the job. A 70B teacher is 140 GB in bf16 — more than the 8B student's entire training state. So for a big teacher you do shard it, or serve it from its own replicas, purely because of weight size rather than because scoring is expensive.

Which model is expensive to run, and the pleasant surprise

In classic off-policy distillation the teacher generates — and generation is the expensive operation, so you pay decode cost at the big model’s price. On-policy distillation reverses the roles:

who generates (expensive)who forward-passes (cheap)
off-policy distillationteacher — the big modelstudent
on-policy distillationstudent — the small modelteacher

So you decode at the cheap model’s price and only score at the expensive model’s price. That is a real part of why the reported Qwen3 comparison lands at 1,800 GPU-hours against RL’s 17,920 — and it is separate from the dense-signal argument in ch. 11.

How Often Do You Update, and How Stale Is Your Data?

The question underneath: after you update, must you re-generate?

Yes. That is what on-policy means, and it is the constraint the entire chapter dances around:

generate with θt → score → update to θt+1 → data is now stale

In the strict version it is one generation round per update and the data is single-use. Everything below is a way of relaxing that to keep GPUs busy — and each rung spends a little more on-policyness.

One GRPO step, traced — the same skeleton as ch. 11's distillation step

Concretely, with DAPO's reported configuration (512 prompts × 16 samples):

// ---- 1. GENERATE (policy, on the inference engine) ----
responses = policy.generate(512 prompts, G=16) // 8,192 sequences
old_log_probs // saved by the GENERATOR
 
// ---- 2. SCORE ----
reward = verifier(responses) // CPU code — 1.0 or 0.0 per response
adv = (reward − group_mean) / group_std // ch. 7, one per RESPONSE
adv = broadcast(adv) // same number onto every token
ref_log_probs = reference(responses) // extra forward pass — ONLY if KL kept
 
// ---- 3. UPDATE (repeat for a few inner epochs) ----
for epoch in range(few):
new_log_probs = policy(responses) // TRAINER's forward
ratio = exp(new_log_probs − old_log_probs)
loss = clipped_loss(ratio, adv)
loss.backward(); opt.step()
 
// then throw the batch away and generate again with the new weights.

Compare it to ch. 11 tab 5's distillation step and the skeleton is identical — generate, score, update. Only step 2 differs:

step 2 does whatGRPO / DAPOon-policy distillation
graderverifier (code) — or an RM in RLHFteacher forward pass
signal granularityone scalar per response, then broadcastone number per token, natively
needs group statistics?yes — mean and std over G samplesno
extra frozen forwardreference, if KL is keptteacher (that IS the signal)

And note where PPO differs from both: its critic is trained, so step 3 also runs a forward and backward through a second model, and step 2 needs the critic's value predictions before the advantage exists at all.

The spectrum, strictest first

rungwhat you dostalenesswhat pays for it

Rung 2 is worth pausing on, because you already studied it as pure theory. Chapter 5 page 1 asks "can we reuse this batch for several updates?" and answers it with the ratio and the clip. That is not an abstract exercise — it is the mechanism that lets rung 2 exist, and rung 2 is why RL frameworks have an "inner epochs" setting at all.

The waiting problem nobody warns you about: stragglers inside one batch

Generator-vs-trainer imbalance is the obvious wait. This is the one that actually hurts:

256 sequences in flight. Length distribution is very skewed:
 
most finish around ~500 tokens
a few run to the cap 20,480 tokens
 
// A synchronous batch is not done until the LAST sequence is done.
// So 255 sequences sit finished while one keeps decoding —
// and decode is sequential, so that tail is ~40x the median length.

Fixes, all of which you have now met: continuous batching (the engine backfills finished slots with new prompts), partial rollouts (rung 4 — park and resume, Kimi k1.5), and simply capping length — which brings back ch. 15’s truncation problem and its overlong reward shaping. Chapter 13 lists this as its own failure mode.

The Failure You Cannot See From the Math

Engine mismatch: your data is off-policy even when the weights are identical

This is the one that surprises people, and it is a direct consequence of having two different pieces of software run the same model.

The generator (vLLM/SGLang) computed log p = −2.30 for this token.
The trainer, at the very same weights, computes −2.28.
 
// Why: different kernels, different batching, different reduction
// order, different precision. Both are "correct" implementations.
 
But old_log_probs came from the GENERATOR, and new_log_probs from
the TRAINER — so ratio = exp(new − old) is wrong for a reason that
has nothing to do with the policy having changed.

So "on-policy" is quietly off-policy by a small, systematic amount that no amount of synchronization removes. And it is much worse for MoE models, where a tiny numeric difference flips a router and sends the token through entirely different experts — chapter 12 has the measured numbers (~10% of routers flip, affecting ~94% of tokens; KL 1.5e-3 vs 6.4e-4 for dense).

Fixes: importance-correct for the gap explicitly (TIS), match precision between the two engines (the FP16 result), or recompute old_log_probs with the trainer so both sides of the ratio come from the same implementation — which costs an extra forward pass but removes the mismatch by construction.

The three-line summary of the whole chapter

1. KV cache, not optimizer state, is what makes this hard.
2. Colocated is the default; disaggregate when generation dominates.
3. Every trick that keeps GPUs busy spends on-policyness — and
ch. 5's ratio and clip are what you spend it with.

Review questions

QuestionOne-line answer
"Can't you just use the training GPUs to generate?"Yes — that is the standard default (verl's HybridEngine). You time-slice: offload the optimizer during generation so the KV cache gets the memory, release the KV cache during training.
"Then why would anyone use separate pools?"KV cache. At 20k-token reasoning traces the cache for a 256-sequence batch is ~640 GB — 5× the training state — so sharing means starving it, and generation is already the bottleneck.
"Why is training 8× the memory of inference?"16 bytes/param (bf16 weights + fp32 master + Adam m and v + gradient) versus 2 for bf16 weights alone.
"After an update, can you reuse the old rollouts?"Not for free — they are now off-policy. PPO's ratio and clip are exactly the licence to do it for a few inner epochs.
"What is staleness and what controls it?"The gap k between the weights that generated a rollout and the weights being updated. Overlap increases k; syncing weights more often decreases it, at the cost of broadcasting ~15 GB per sync for an 8B model.
"Where does the teacher live in on-policy distillation?"Usually co-resident with the trainer — forward-only, so 2 bytes/param and no optimizer state, doing one forward pass per batch. Shard it only if the teacher is large.
"What is the biggest source of idle GPU time?"Stragglers within a batch: a synchronous step waits for the longest sequence, and the tail can be ~40× the median. Fixed by continuous batching or partial rollouts.
"How can on-policy data still be off-policy?"Engine mismatch — the inference engine and the trainer compute slightly different log-probs at identical weights, so the ratio is wrong independent of drift. Worst on MoE, where routers flip.
"You have one node and 2k-token responses. What layout?"Colocated, synchronous, no question — the KV cache is ~8 GB, complexity buys you nothing.
