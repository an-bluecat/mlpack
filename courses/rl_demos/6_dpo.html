Chapter 6: DPO

Direct Preference Optimization — skip the reward model, train directly from human choices

First: What RLHF Actually Does (Concrete)

RLHF is a 3-step pipeline

Chapter 5 (pages 4-6) taught this pipeline step by step: preference pairs → reward model → PPO with a KL leash. Quick recap with actual data — because DPO's whole pitch is deleting most of it:

Step 1: Collect human preferences

Show a human two responses to the same prompt. They pick the better one.

PromptResponse AResponse BHuman picked
"Tell me a joke""Why did the chicken cross the road? To get to the other side!""I am an AI and cannot tell jokes."A
"What is 2+2?""2+2 is the sum of two and two""4"B
"Write a haiku""Roses are red...""Silent winter moon / frost clings to the bare branches / a crow calls at dawn"B

Typically ~50,000-100,000 of these pairs.

Step 2: Train a reward model

A separate neural network that takes (prompt, response) and outputs a score:

reward_model("Tell me a joke", "Why did the chicken...") → 0.82
reward_model("Tell me a joke", "I am an AI and cannot...") → 0.15
 
// Trained so that: score(human_preferred) > score(human_rejected)
// 0.82 > 0.15 ✓ — matches what the human picked

The reward model learns to imitate the human's taste. Given any new (prompt, response) pair, it guesses what score the human would give.

(0.82 and 0.15 are readable stand-ins, not probabilities — the RM's head is a bare Linear(4096,1) with no sigmoid, so real scores are any real number, and only the gap between two of them means anything. Ch. 5 tab 4 has the wiring.)

Step 3: Run PPO using the reward model as the "environment"

// For each training prompt:
prompt = "Tell me a joke"
response = LLM.generate(prompt) // LLM writes a response
reward = reward_model(prompt, response) // → 0.65
 
// PPO update (same as Chapter 5):
// ratio = new_prob / old_prob
// clipped loss = -min(ratio * advantage, clip(ratio) * advantage)
// update LLM weights

The problem with this pipeline

Step 2 (reward model) is a whole separate model you have to train and maintain. It can be:

  • Wrong — it might give high scores to responses the human wouldn't actually like
  • Exploitable — the LLM can find weird responses that score high on the reward model but are actually bad ("reward hacking")
  • Expensive — you're training and running two large models instead of one

DPO's insight: what if we skip step 2 and 3 entirely?

DPO: Train Directly on Preferences

The one new concept

Instead of:

preferences → reward model → PPO → updated LLM

DPO does:

preferences → updated LLM   (directly)

No reward model. No PPO. No clipping. One training loop.

How? Use the LLM itself as the reward model

An LLM already assigns probabilities to text. If the LLM says P("Why did the chicken...") = 0.03 and P("I cannot help") = 0.01, then the LLM already "prefers" the chicken joke (higher probability).

DPO's math proves: there's a direct formula to go from preference pairs to the optimal LLM update, without ever building a separate reward model.

RLHF (3 steps)

1. Collect preferences

2. Train reward model

3. Run PPO (generate, score, clip, update)

Two models. Sampling in the loop. Hyperparameter-sensitive.

DPO (1 step)

1. Collect preferences

2. Single supervised-style training loop

One model. No sampling in the loop. Simple as fine-tuning.

One Preference Pair — Only Probabilities

For this whole tab, pretend there are only two possible answers

AnswerHuman feedback
“Why did the chicken cross the road?”Winner
“I cannot help with that.”Loser

That is all standard DPO receives from the human: the first answer won. It normally does not receive “winner = 0.9” and “loser = 0.8.”

Your proposed loss is understandable—but it is not DPO

Suppose we happened to ask the human for numeric ratings:

human winner score = 0.9
human loser score  = 0.8
human difference   = 0.9 − 0.8 = +0.1
 
current winner probability = 0.48
current loser probability  = 0.52
current difference          = 0.48 − 0.52 = −0.04
 
your error = +0.1 − (−0.04) = 0.14

This could define a custom training rule. But it assumes that human ratings and model probabilities use the same measuring stick. They do not.

ProblemConcrete reason
Usually no human scoresThe dataset says only “A beats B.” The number 0.9 was never collected.
Rating scale is arbitraryOne rater may write 0.9 vs 0.8; another may mean the same preference with 9 vs 8. Your error changes from 0.14 to 1.04 even though the choice is identical.
No justified probability targetA human score gap of 0.1 does not imply that the model’s probability gap should become exactly 0.1.

Keep the good part of your idea: compare winner against loser. Drop the unsupported part: treating human ratings as target model probabilities.

The preference update has moved in the right direction: the winner grew relative to its starting probability, while the loser shrank. It has not finished—the winner is still below the loser—so training should continue.

The probability-only DPO idea

For each answer, ask:

winner change = current winner probability ÷ reference winner probability
               = 0.48 ÷ 0.40 = 1.20
 
loser change  = current loser probability ÷ reference loser probability
               = 0.52 ÷ 0.60 = 0.87

Desired direction: winner’s change should be larger than loser’s change.

The reference is therefore not another human score. It is the model’s frozen “before” picture. DPO asks whether preference training changed the winner more favorably than it changed the loser.

First try at a loss — and the disease it catches

We want the winner’s change to beat the loser’s change. Simplest possible loss: their difference.

gap  = winner change − loser change = 1.20 − 0.87 = +0.33
loss = −gap = −0.33   // training pushes loss down = widens the gap

This works — and never stops working. The pair stays in the dataset; every epoch pushes the gap wider, forever. That is chapter 5 page 0 all over again: a push with no notion of “done,” grinding the same direction until the model collapses onto a handful of winner phrasings.

What we actually want: push hard while the model has the pair backwards, fade to zero once it clearly agrees with the human.

Turn the gap into a belief — and your rule comes back

To know when to fade, ask the gap a yes/no question: “how convinced are you that the winner wins?” The sigmoid is the standard converter — it squashes any number into a value between 0 and 1, with 0 mapping to 0.5:

gap−2−0.330+0.33+1.5+2.75
belief = sigmoid(gap)0.120.420.500.580.820.94

(Its formula is 1/(1+e−gap) — you never compute it by hand; the table is the behavior. Before training, both changes are 1.0, so gap = 0 and belief = 0.50: “no opinion.” Exactly right for a model that hasn’t seen the pair yet.)

Now the pieces of your proposed rule snap into place — in belief space, where both sides finally use the same measuring stick:

target belief  = 1    // the human picked the winner — that’s the whole label
current belief = sigmoid(+0.33) = 0.58
push strength = target − current = 1 − 0.58 = 0.42

This IS “human says minus model currently believes” — your rule — just measured on beliefs about who wins (both sides live in 0–1) instead of on raw response probabilities (where a 0.9 rating and a 0.030 product share no scale).

Watch it fade as training continues on this pair:

training stagewinner / loser changegapbeliefpush = 1 − belief
start1.00 / 1.0000.500.50
now1.20 / 0.87+0.330.580.42
later (suppose 2.0 / 0.5)2.0 / 0.5+1.50.820.18
much later (suppose 3.0 / 0.25)3.0 / 0.25+2.750.940.06

Learned pairs go quiet on their own; a pair the model has backwards (gap −2, belief 0.12) shouts with push 0.88. Same shape as REINFORCE’s (1−p): already-confident → small push.

(The exact recipe on the next tab measures the gap slightly differently — in logs, scaled by β — but the sigmoid and the push rule carry over unchanged.)

“Wait — why not just put the sigmoid straight on the probabilities?”

Natural question, and the direction is completely right: apply the belief rule directly to the two raw probabilities, no reference model anywhere.

gap = P(winner) − P(loser) = 0.030 − 0.010 = 0.020
belief = sigmoid(0.020) = 0.505
push = 1 − 0.505 = 0.495

Winner goes up, loser goes down — exactly as intended. The failure is not the direction, it is the size. Whole-response probabilities are tiny, so their difference is tiny, so the belief is pinned at “no opinion” no matter what the model actually thinks.

And it cannot escape, because probabilities live in 0–1. Take the most extreme case that could ever exist:

// perfect confidence: winner at 1.0, loser at 0.0
gap = 1.0 − 0.0 = 1.0
belief = sigmoid(1.0) = 0.731 // the absolute ceiling
push = 0.269 // the absolute floor

So belief is trapped between 0.269 and 0.731. Two consequences, both bad:

  • The model can never express certainty — 73% is the most conviction the loss can ever read off it.
  • The push never fades below 0.269, so every pair keeps shouting forever. That destroys the self-weighting behaviour this tab just built, where solved pairs go quiet on their own.

Now compare the reference-ratio version from the cards above: winner 1.20× vs loser 0.87× gave gap 0.33 and belief 0.58 — and as training proceeds (2.0 vs 0.5) the gap reaches 1.5 and belief 0.82, with no ceiling at all. A ratio is unbounded; a probability difference is not. That is the real reason the comparison is built from ratios.

There is a way to rescue your version — measure the responses on a log scale instead of a raw one, which unbounds the gap. That turns out to be a real, published family of methods; the next tab shows the step, and chapter 14 is the method built on exactly it.

Stop here before the compact formula

You now have the complete idea without new mathematical machinery:

1. Human says which response won.
2. Reference model stores both starting probabilities.
3. Current model produces both current probabilities.
4. Measure how much each response changed from its own starting point.
5. gap = winner’s change minus loser’s change.
6. sigmoid turns the gap into a belief (0–1) that the winner wins.
7. Push with strength = 1 − belief: hard while the model disagrees with the human, fading to zero as it agrees.

The next tab changes the arithmetic into the numerically stable form used by real code. It should be read as a translation of these seven steps—not as a new idea.

The Same Step — Now Translate It Into the Exact DPO Loss

What this tab adds — and what it does not

Tab 2.1 already settled the idea: compare the winner’s current-vs-reference change against the loser’s, and push with strength 1 − belief. None of that changes here.

This tab adds exactly one new thing: the ratios from tab 2.1 cannot be fed to the loss as they stand, because the loss subtracts the two scores and raw ratios are lopsided under subtraction. Fixing that is where the log comes from — earned in the "where the score comes from" card below, not assumed. Everything else on this tab is arithmetic on numbers you have already seen.

Setup

We have one preference pair:

PromptWinner (yw)Loser (yl)
"Tell me a joke""Why did the chicken cross the road?""I cannot help with that."

We also need a reference model — a frozen copy of the LLM from before training started. This prevents the LLM from changing too much (same idea as PPO's clipping, just done differently).

Step 0: What is "the probability of a whole response"?

An LLM outputs a probability for one token at a time. A whole response's probability is the product of its tokens' probabilities, each conditioned on everything before it:

// response tokenized: ["Why", " did", " the", ...]
P(response | prompt) = P("Why"|prompt) × P(" did"|prompt+"Why") × P(" the"|prompt+"Why did") × ...
 
// tiny 3-token example:
0.5 × 0.3 × 0.2 = 0.030 // ← this is where a number like 0.030 comes from
 
// in code you work in log space — the product becomes a SUM:
log P(response) = log(0.5) + log(0.3) + log(0.2)
                = −0.693 − 1.204 − 1.609 = −3.507 // = log(0.030) ✓
Refresher: reading logs — "what day is it?"

Step 1 — start with base 2, and forget e entirely. One bacterium on day 0. It doubles every day. Then log₂(x) asks one question: "I see x bacteria — what day is it?"

day01234
amount124816
log₂01234

That's the whole definition: log₂(8) = 3 because 8 is what you have on day 3.

Step 2 — fractions are days BEFORE day 0. Run the film backwards; it halves each day:

day−3−2−10
amount1/81/41/21
log₂−3−2−10

So log₂(1/8) = −3 — three days before, not eight. (Count the halvings: ½, ¼, ⅛.) A negative log just means "before the starting day," i.e. the amount is below 1.

Step 3 — in-between amounts are mid-day. 10 isn't a power of 2; it sits between day 3 (=8) and day 4 (=16):

log₂(10) = 3.32   // a third of the way into day 3

Step 4 — why huge numbers give small answers. Say it in days and the strangeness disappears:

log₂(1,000)     ≈ 10 days   // 2¹⁰ = 1024
log₂(1,000,000) ≈ 20 days   // 2²⁰ = 1,048,576
log₂(0.001)     ≈ −10 days  // ten days BEFORE day 0

A thousand times bigger costs only 10 more days — the growth is exponential, so the calendar barely moves. Logs are small because days are cheap.

Step 5 — and here is why products become sums. Multiplying amounts = adding days:

8 is day 3,  4 is day 2
8 × 4 = 32  →  day 3 + 2 = 5   // 2⁵ = 32 ✓
 
// "multiply by 4" = "wait 2 more days". Always.
log(a × b) = log(a) + log(b)

That rule is exactly why the product of token probabilities above becomes a sum of logs.

Step 6 — now change the clock. That is all a "base" is. Base 2 = doubles per day; base 10 = ×10 per day:

log₁₀(1,000) = 3 days   // 10 → 100 → 1000
log₁₀(0.001) = −3 days

Same story, faster clock — so fewer days for the same amount. The base only sets how big one "day" is.

Step 7 — ln is that same clock with base e ≈ 2.718. Why such a strange number? Because this one doesn't jump at midnight — it grows continuously, at every instant gaining 100% of its current size per unit time. Run that from 1 for one full time unit and you land on 2.718; that is what e means. So:

ln(x) = how much TIME does continuous growth need to get from 1 to x?
 
ln(1)     = 0      // already there
ln(2)     = 0.693  // doubling takes 0.693 time units...
ln(2.718) = 1      // ...and one FULL unit overshoots to 2.718
ln(10)    = 2.303
ln(0.5)   = −0.693 // same trip, backwards

Note doubling costs less than one time unit (0.693, not 1) — continuous compounding arrives before the once-a-day version does.

The payoff — near 1, ln(x) IS the percent change. At x = 1 the growth rate is exactly 1 per unit time, so gaining 1% takes about 0.01 of a time unit:

ln(1.01) = 0.00995 ≈ +1%
ln(1.05) = 0.0488  ≈ +5%
ln(1.20) = 0.182   ≈ +20% // ~9% low by here, still readable

And that last line is this chapter: Step 2's log_ratio_w = +0.182 is just 0.030/0.025 = 1.20 — the winner became 1.20× as likely, the exact 20% increase from tab 2.1. Same fact, different clothes. (The loser's −0.182 is 1/1.2 — the same trip backwards.)

Four anchors rebuild every number in this chapter, using log(a×b) = log a + log b from Step 5:

ln 1 = 0    ln 2 = 0.693    ln 3 = 1.099    ln 10 = 2.303 // so ln 100 = 4.605
 
ln 0.030 = ln 3 − ln 100 = 1.099 − 4.605 = −3.507 // ✓ Step 0
ln 0.025 = ln 2.5 − ln 100 = 0.916 − 4.605 = −3.689 // ln2.5 = ln5 − ln2
ln 0.010 =        − ln 100 = −4.605
ln 0.012 = ln 1.2 − ln 100 = 0.182 − 4.605 = −4.423

A probability is always below 1, so its log is always a negative time — how far back before day 0 you would have to start. A 30-token response at ~10⁻⁹ sits at −20.7: comfortably readable, instead of underflowing to zero as a raw product.

The deep reason every loss here uses logs: a log turns a ratio (asymmetric, lives in 0→∞, with 1 as an awkward middle) into a difference (symmetric, −∞→∞, with 0 as the natural middle) — comparing two amounts multiplicatively becomes subtracting two clock readings. Bradley-Terry, DPO, and the PPO ratio all compare two quantities multiplicatively; the log is what makes that a plain subtraction the optimizer can work with.

Keep that −3.507 in mind — it shows up again in Step 2. Long responses have tiny products (30 tokens at ~0.5 each ≈ 10−9), which is exactly why everything runs in log space.

Step 1: Get probabilities from both models

Both the current LLM and the frozen reference assign a probability to each response:

// Current model (the one we're training):
P_current("Why did the chicken..." | prompt) = 0.030
P_current("I cannot help..." | prompt) = 0.010
 
// Reference model (frozen, never changes):
P_ref("Why did the chicken..." | prompt) = 0.025
P_ref("I cannot help..." | prompt) = 0.012

Step 2: Compute log-ratios

"How much more does the current model like this response compared to the reference?"

// For the winner:
log_ratio_w = log(0.030) - log(0.025)
            = -3.507 - (-3.689)
            = +0.182 // current model likes winner MORE than ref does ✓
 
// For the loser:
log_ratio_l = log(0.010) - log(0.012)
            = -4.605 - (-4.423)
            = -0.182 // current model likes loser LESS than ref does ✓

Why is subtracting two logs called a "log-ratio"? Because it is one — dividing is the mirror of the rule from Step 0's refresher (multiply → add, so divide → subtract):

log(a) − log(b) = log( a / b )
 
log(0.030) − log(0.025) = log( 0.030/0.025 ) = log(1.20) = +0.182
// ← the winner is 1.20× as likely as before: tab 2.1's exact number

The four numbers in one picture — where each one flows

Follow one row: the same response is scored by the trainable model and the frozen reference, and only their ratio survives — "how much has my opinion of this response moved since training began?" The sigmoid node is tab 2.1's belief converter, unchanged. The winner's movement (+0.182) and the loser's movement (−0.182) then fight in the gap: the loss only goes down if the winner's ratio outgrows the loser's. Nothing is generated anywhere in this picture — that's why DPO is off-policy (chapter 9) and why it's so cheap.

Before the loss: where the score comes from (and why it grows a log)

Notation first. y is standard shorthand for one response — a sentence. So score(y) means "the score of that response," and we compute it twice per pair: score(winner) and score(loser). Nothing else hides in y.

What we need. Chapter 5's loss takes exactly one number per response:

loss = −log( sigmoid( score(winner) − score(loser) ) ) // Bradley-Terry
 
// In ch. 5 that number was RM(y): the output of a separate network's
// Linear(4096,1) head. A raw, unbounded number. NO log anywhere.
// DPO deletes that network. So: which number from the LLM replaces it?

Attempt 1 — just use the probability. score(y) = P_current(y). The LLM already produces it, so try it:

score(winner) = 0.030,  score(loser) = 0.010   // gap = 0.020
 
// BROKEN — it measures length and phrasing, not quality:
// short, bland reply (4 tokens)      P ≈ 0.010
// long, excellent reply (30 tokens)  P ≈ 0.000000001
// The good answer scores ~10 million times WORSE purely for being
// longer — every extra token multiplies in another number < 1.

Attempt 2 — compare each response against ITSELF. This is tab 2.1’s move, and it kills attempt 1’s length problem outright: put the same sentence on top and bottom, and whatever made it long or unusual divides out. Give the two ratios short names, because we are about to differentiate them:

W = P_cur(winner) / P_ref(winner) = 0.030 / 0.025 = 1.20 // winner got 1.20× likelier
R = P_cur(loser)  / P_ref(loser)  = 0.010 / 0.012 = 0.83 // loser got 0.83× as likely

So put those straight into chapter 5’s loss and see what happens. No log anywhere yet — just the ratios:

z = W − R = 1.20 − 0.83 = 0.37
Loss = −ln sigmoid(z)

This is a perfectly reasonable proposal, and you cannot tell whether it works by looking at it. Chapter 5’s first principle: the optimizer never reads the loss, only its derivative. So differentiate it.

Differentiate, part 1 — the easy links.

// outer link (chapter 5 derived this one):
dLoss / dz = −( 1 − sigmoid(z) ) = −(1 − 0.591) = −0.409
 
// inner link: z contains R = P_cur(loser)/P_ref(loser), and
// P_ref(loser) is a frozen constant divisor, so:
dz / d P_cur(loser) = −1 / P_ref(loser) = −1 / 0.012
 
// multiply them:
dLoss / d P_cur(loser) = 0.409 / 0.012 = +34.1

Positive, so gradient descent lowers the loser’s probability. Correct direction — nothing is broken yet.

Stop — "how big is that push?" does not have an answer yet

34.1 is a big-looking number, but big compared to what? Before we can call this push weak or strong we have to decide what variable we are measuring the push on. That sounds like a technicality. It is not: the two obvious choices give opposite answers about which response is being pushed harder. So this step has to be settled properly.

Step 1 — the only thing that ultimately matters is the gradient on the weights. dLoss/dθ. Probabilities do not move on their own; weights move, and everything else follows.

Step 2 — write that gradient out. Here is the key structural fact: both candidate losses depend on θ only through the two log-probabilities. (Obvious for the log version. True for the raw-ratio version too, because P_cur = e^(log P_cur).) So the chain rule always produces this shape:

dLoss/dθ = c_w · ∇θ log P(winner) + c_l · ∇θ log P(loser)

Step 3 — the ∇ terms are not yours to choose. ∇θ log P(y) is fixed by the network’s weights and by which tokens response y happens to contain. No choice of loss function can change them.

Step 4 — therefore the loss’s entire influence is those two scalars. c_w and c_l are the whole of your design; everything else in the gradient is the network being itself. And by definition:

c = dLoss / d( log P )

That is the answer to "why log P and not P". The log-probability gradient is not a convention or a convenience — it is precisely the coefficient the loss contributes, isolated from the network’s fixed structure. Measuring in probability space instead gives you dLoss/dP = c / P, which multiplies your design choice by the response’s own probability and therefore hides the very thing you are trying to inspect.

And this is not cosmetic — the two currencies disagree about who wins. Same loss, same numbers:

measured onpush on winnerpush on loserverdict
probability, dLoss/dP0.409 × 1/0.025 = 16.40.409 × 1/0.012 = 34.1loser pushed 2.08× harder
log-probability, dLoss/d(log P)0.409 × W = 0.4910.409 × R = 0.341winner pushed 1.44× harder

Exactly opposite conclusions. The log-probability row is the true one, because those two numbers are the c values from step 2 — the actual weights the loss puts on each response’s contribution to dθ. The probability row is the same information smeared by a factor of P, which differs between the two responses and so scrambles the comparison.

Supporting intuition: why probability is a bad ruler in the first place

Independently of the argument above, absolute probability changes are simply not comparable across responses:

the moveabsolute changemultiplicative change
0.010 → 0.012+0.002×1.2
0.500 → 0.600+0.100×1.2

Same ×1.2, 50× different in absolute terms. Money is the familiar version: a $1,000 raise means everything at a $20,000 salary and nothing at $2,000,000, which is why nobody quotes raises in dollars. Logs are the ruler on which equal factors are equal distances — the "what day is it?" refresher on this tab, where every doubling is one same-sized step.

The conversion, made concrete. Since P = e^(log P), differentiating an exponential returns itself: dP / d(log P) = P. Check it by hand at P = 0.010:

log P = −4.605  →  P = 0.01000
nudge log P up by 0.01, to −4.595  →  P = 0.01010
 
ΔP / Δ(log P) = 0.000100 / 0.01 = 0.0100 = P   // ✓

Differentiate, part 2 — convert the push into that currency. Multiply by P_cur(loser):

dLoss / d( log P_cur(loser) ) = 34.1 × 0.010 = +0.341
 
// and in symbols, watch what the two factors collapse into:
( 1−sigmoid(z) ) / P_ref(loser) × P_cur(loser)
= ( 1−sigmoid(z) ) × P_cur(loser) / P_ref(loser)
= ( 1−sigmoid(z) ) × R    = 0.409 × 0.83 = 0.341 ✓

The frozen 1/P_ref(loser) and the conversion’s ×P_cur(loser) combine into R itself. Same for the winner, giving ×W:

push DOWN on loser  = (1−sigmoid(z)) × R = 0.409 × 0.83 = 0.341
push UP on winner   = (1−sigmoid(z)) × W = 0.409 × 1.20 = 0.491

There is the defect: the loser stalls

The loser’s push is proportional to R — and R is small precisely because you have been succeeding at pushing the loser down. So success weakens the very force producing it. Factor out (1−sigmoid(z)) to see it alone:

where the loser isRpush down on loser
untouched1.01.00 × (1−sigmoid)
2× less likely0.50.50 × (1−sigmoid)
10× less likely0.10.10 × (1−sigmoid)
100× less likely0.010.01 × (1−sigmoid)

The loser asymptotes: it can never be driven properly down, because the closer it gets to zero the weaker the push becomes. Meanwhile the winner’s push, proportional to W, grows as it wins. Take the cleanest case — two symmetric events:

winner became 2× MORE likely  →  W = 2.0
loser  became 2× LESS likely  →  R = 0.5
 
// the same size of change, in opposite directions. But:
|winner push| / |loser push| = W / R = 2.0 / 0.5 = 4
// the winner is pushed FOUR TIMES harder for an equal-sized event.

And none of this was visible in the loss. The gap z = 0.37 looked perfectly healthy — the flaw is entirely in how that one gap gets distributed between the two responses.

Attempt 3 — take the log of each ratio, and the distribution problem vanishes. Because a log turns the division into a subtraction, the reference term becomes an additive constant, and its derivative is exactly 1:

u = log W − log R
= log P_cur(winner) − log P_ref(winner) − log P_cur(loser) + log P_ref(loser)
└── constant ──┘ └── constant ──┘
 
du / d( log P_cur(winner) ) = +1     du / d( log P_cur(loser) ) = −1
 
// no W, no R — so the pushes are:
push UP on winner   = (1 − sigmoid(u)) = 0.410
push DOWN on loser  = (1 − sigmoid(u)) = 0.410
// (u = 0.182 − (−0.182) = 0.365, sigmoid(0.365) = 0.590)

Exactly equal and opposite, at every stage of training. No stall, and a symmetric pair of events gets a symmetric pair of pushes. This is also the property the gradient card lower down this tab quotes as a fact ("UP with strength 0.0491 / DOWN with strength 0.0491") — the log is what makes it true.

log ratio (attempt 3)(1−sigmoid)(1−sigmoid)yes, always

Two honest footnotes. (1) The symmetry above is a real mechanical property, but the primary reason DPO uses a log is that the theory produces it: the KL-regularized objective’s optimum is β·log(P_cur/P_ref), not a design choice. (2) The reference model is doing two jobs here — fixing attempt 1’s length problem and anchoring the model. Chapter 14 keeps the log but drops the reference, dividing by token count instead.

Last piece — β is a unit conversion. The log-ratio is in "how far the model moved" units; the loss wants "reward" units. β sets the exchange rate, and it isn't arbitrary: it falls out of the KL-regularized objective on the next tab, where β is the same knob that says how expensive drift is.

score(y) = β × log( P_current(y) / P_ref(y) ) // the "implicit reward"
 
score(winner) − score(loser) = β × (0.182 − (−0.182)) = β × 0.364
// ...which is exactly the "gap" computed in Step 3 below.
Footnote: the theory's version has an extra term — and it cancels

The exact result from the DPO paper is score(y) = β·log(P_cur(y)/P_ref(y)) + β·log Z(prompt). That second term is ugly and impossible to compute — but it depends only on the prompt, not on the response. Winner and loser share the same prompt, so it is identical for both and vanishes in the subtraction:

score(w) − score(l) = β(log_ratio_w + log Z) − β(log_ratio_l + log Z)
                    = β(log_ratio_w − log_ratio_l)   // Z is gone

This is the same thing ch. 5 said about the reward model: only the GAP means anything, add a constant to every score and the loss is unchanged. That property is exactly what makes the uncomputable term harmless.

The loss it plugs into is the Bradley-Terry model, derived from scratch in the optional aside 5a. This substitution IS the DPO paper — its math shows this score is what the optimal reward model would have been. The paper's actual subtitle: "Your Language Model is Secretly a Reward Model." Page 1 said "use the LLM itself as the reward model" — this is where that happens.

And sigmoid turns a score gap into a probability, exactly like in ch. 5: gap 0 → 0.5 (coin flip: "no idea who wins"), big positive gap → near 1.0 ("winner clearly wins").

Step 3: The DPO loss

Tab 2.1 ended with a push rule: strength = 1 − belief. But an optimizer doesn’t take rules — it takes a loss and differentiates it. So we need the loss whose gradient is that rule. That loss is −log(belief): near-certain belief → loss near 0; belief 0.5 → loss 0.69; belief near 0 (model has the pair backwards) → loss huge. The last card on this tab checks that its gradient comes out to exactly 1 − belief.

// β comes from the penalty for drifting away from the reference
β = 0.1
 
// Gap = how much more the model prefers winner over loser
gap = β × (log_ratio_w - log_ratio_l)
     = 0.1 × (0.182 - (-0.182))
     = 0.1 × 0.364
     = 0.0364
 
// Loss = -log(sigmoid(gap))
sigmoid(0.0364) = 0.509 // barely above 0.5 — model slightly prefers winner
loss = -log(0.509) = 0.675
 
// If the model strongly preferred winner: sigmoid → 0.99, loss → 0.01 (tiny)
// If the model preferred loser: sigmoid → 0.01, loss → 4.6 (huge!)
// Loss pushes the model to widen the gap between winner and loser.

Step 4: Backprop and update

loss.backward() // compute gradients
optimizer.step() // update LLM weights
 
// After update:
P_current("Why did the chicken..." | prompt) = 0.032 // went UP ✓
P_current("I cannot help..." | prompt) = 0.009 // went DOWN ✓
 
// The reference model stays frozen. It never changes.
// It's the anchor that prevents the LLM from drifting too far.

Winner got more likely, loser got less likely. That's one DPO step. Repeat for all 50,000 preference pairs.

What the gradient actually does — one number steers everything

// Differentiate loss = −log(sigmoid(gap)). The chain rule leaves
// ONE scalar in front of everything (times the learning rate):
 
push strength = β × (1 − sigmoid(gap))   // = β × (1 − belief): tab 2.1’s rule,
//                                         recovered automatically by backward()
              = 0.1 × (1 − 0.509)
              = 0.1 × 0.491 = 0.0491
 
log P(winner) pushed UP   with strength 0.0491
log P(loser)  pushed DOWN with strength 0.0491
 
// Read (1 − sigmoid(gap)) as "how wrong am I still?":
// model barely prefers winner (0.509, our case) → strong push (0.491)
// model strongly prefers winner (0.99) → tiny push (0.01)
// model prefers the LOSER (0.10) → huge push (0.90)

So pairs the model already gets right fade out automatically, and pairs it gets backwards shout the loudest. Self-weighting, for free — the same "already-confident → small push" behavior you saw in the REINFORCE gradient (1−p), wearing a different formula.

The big gotcha: Step 4 said "winner went UP ✓" — in real runs it often DOESN'T

Walk the chain, because each link matters:

// (1) The loss only ever sees the GAP. Any weight change that widens
// the gap lowers the loss — INCLUDING one where both responses fall:
 
// before after (illustrative of the documented pattern)
log P(winner)   −3.507 (P=0.030)   −4.0 (P=0.018)   // FELL 40%!
log P(loser)    −4.605 (P=0.010)   −6.0 (P=0.0025) // fell faster
margin         1.098              2.0    // gap GREW → loss went DOWN ✓?!
 
// The loss is perfectly happy. Your good answer just got LESS likely.

(2) Why would the winner fall at all? Both probabilities come from the same shared weights — and, worse, often from shared tokens. Take a pair that differs by one word:

winner = "two plus two is four"
loser  = "two plus two is five"   // 4 of 5 tokens SHARED
 
// Pushing the loser down = pushing down P("two"), P("plus"|two), ...
// — tokens that are 4/5 of the WINNER too. The winner gets dragged
// down with it; the margin still widens through the final token.
// (The DPOP paper showed this is worst exactly when pairs are similar
// — small edit distance, like math answers differing in one number.)

(3) Where does the lost probability go? Each token position is a softmax — mass is conserved. If winner AND loser both sink, the freed mass flows to responses that are neither: text nobody ever vetted. Researchers call this likelihood displacement, and it can silently unalign the model — you trained on good pairs and made unvetted text more likely.

(4) The fix: anchor the winner in absolute terms, not just relative ones:

// Simplest form (RPO-style): bolt a plain SFT term onto the loss —
loss = dpo_loss + λ × ( −log P_current(winner) )
// ↑ gap machinery ↑ "and ALSO keep the winner likely, period"
 
// DPOP variant: penalize only when the winner sinks below its start —
penalty = max(0, log P_ref(winner) − log P_current(winner))
// fires only if the winner fell below the reference; zero otherwise.

What to watch in a real run: log the margin AND log P(winner) separately. Margin rising while log P(winner) falls = displacement in progress — the single most useful DPO training-curve diagnostic.

β and the Reference Model: Don't Drift Too Far

Which of chapter 5's two leashes is β?

Chapter 5 ended with two different restraints, and they are not interchangeable — page 6 there contrasts them directly. β is the second one:

RestraintMeasures againstLimitsDPO's counterpart
PPO's clipπ_old — re-snapshotted every batchchange per batch (a speed limit)none — DPO takes no repeated steps on stale data
PPO's KL leashπ_ref — frozen forevertotal drift, ever ("stay near home")β and the frozen reference

DPO needs no clip because it never reuses a batch across epochs against a moving snapshot — there is no sampling loop to go stale. What it does need is the total-drift guarantee, and that is exactly what β buys, measured against the same kind of frozen π_ref.

First fix the direction: larger β means a stronger anchor

DPO begins from the same goal as KL-regularized RLHF:

goal = human reward − β × distance from reference
 
β = 0.50 → each unit of distance costs 0.50 // stronger anchor
β = 0.10 → each unit of distance costs 0.10
β = 0.01 → each unit of distance costs 0.01 // weaker anchor

Therefore, all else equal, larger β favors staying closer to the reference; smaller β permits more deviation.

One subtlety: β also appears inside DPO’s classification loss, so you should not look at one loss number and interpret it directly as “leash length.” Its meaning comes from the KL-regularized objective from which DPO was derived.

The reference model: a frozen "before" snapshot

// Before DPO training:
reference_model = copy(LLM) // exact clone
reference_model.freeze() // never updated again
 
// During training:
// LLM weights change → P_current changes
// reference stays frozen → P_ref stays the same
// log_ratio = log(P_current / P_ref) measures "how far have I drifted?"
 
// If the LLM drifts too far from reference on the LOSER response:
// log_ratio_l becomes very negative → gap shrinks → loss increases
// "You're changing too much — stay closer to who you were."

The DPO training loop — complete pseudocode

// Setup
reference = frozen_copy(LLM)
β = 0.1
 
// For each preference pair in dataset:
for (prompt, winner, loser) in preference_data:
 
  // 1. Get log-probs from both models
  log_ratio_w = log P_current(winner|prompt) - log P_ref(winner|prompt)
  log_ratio_l = log P_current(loser|prompt) - log P_ref(loser|prompt)
 
  // 2. Compute loss
  loss = -log(sigmoid(β × (log_ratio_w - log_ratio_l)))
 
  // 3. Update (plain gradient descent — no PPO, no clipping, no sampling)
  loss.backward()
  optimizer.step()

That's it. No reward model to train. No episodes to sample. Just a supervised-style loop over preference pairs.

"Less data" — is that a problem?

You asked: DPO uses a fixed dataset of preference pairs. PPO generates fresh data every step. Doesn't DPO see less?

Yes, and here's what that means concretely:

// PPO training (simplified):
Step 1: generate 1000 responses to 1000 prompts // fresh data
Step 2: score them with reward model
Step 3: update LLM
Step 4: generate 1000 NEW responses // model changed, so new outputs
Step 5: score them, update again...
 
// After 100 steps: PPO has seen 100,000 unique model-generated responses
// Each one was generated AFTER the previous update, so they reflect
// the model's current state. The data is always "fresh."
 
// DPO training:
Dataset: 50,000 (prompt, winner, loser) pairs // collected ONCE, before training
Epoch 1: loop through all 50,000 pairs
Epoch 2: loop through the SAME 50,000 pairs again
Epoch 3: same pairs again...
 
// The model keeps seeing the same examples. As it improves,
// the easy pairs become useless (model already gets them right)
// but there's no way to generate harder examples.

When this matters: complex tasks like coding or math, where the model needs to discover novel strategies through exploration. PPO's sampling helps here.

When it doesn't matter: style alignment ("be polite", "don't be preachy"), where the preference data already covers the space well. DPO works great here.

Review questions with short answers

QuestionThe one-line answer
"Why can DPO skip the reward model?"The LM's own log-ratio vs the reference — β·log(Pcur/Pref) — IS a reward score; plug it into the same Bradley-Terry loss the RM would have been trained with, and the RM becomes redundant.
"Is DPO reinforcement learning?"Mechanically no — no sampling, no advantage, fixed dataset, supervised-style loop; mathematically it's the closed-form optimum of the same KL-leashed RLHF objective.
"Can the winner's probability go DOWN during DPO?"Yes, routinely — the loss only sees the margin, and similar pairs share tokens, so both can sink while the gap widens (likelihood displacement); fix = DPOP/RPO anchor on the winner.
"What breaks with β too small? Too large?"Too small: weak anchor, model drifts far from the reference and degrades fluency; too large: strong anchor, barely moves, preferences underfit.
"DPO is offline — so what goes wrong?"The pairs came from some other policy; as the model changes, it's being corrected on responses it would never produce — online/iterated DPO regenerates pairs from the current policy.
"When would you pick PPO/GRPO over DPO?"When reward is verifiable per response (math/code — no pairs needed) or you need the model to explore its OWN outputs, not text some earlier policy wrote.
"Both responses in a pair are bad — what does DPO learn?"It still pushes the 'less bad' one up relative to the other — garbage-in-pairs teaches 'least bad' preferences; KTO-style absolute labels handle this better.

Where DPO sits on the map you'll need later

DPO trains on a fixed dataset of pairs that some other policy generated — in the vocabulary of chapter 9, it is off-policy. That's the deep reason behind both cons in the table above (stuck with your dataset, needs good pairs): the model never trains on its own current behavior. Everything after GRPO in this course — chapters 8-12 — is about what changes when you pay for on-policy data.
