Chapter 5: PPO

Proximal Policy Optimization — the algorithm behind ChatGPT's RLHF

The Catastrophic Update Problem

Actor-Critic's weakness

Imagine the agent has been training well for 200 episodes. Then one outlier episode happens:

# Episode 201: a wild lucky episode
# The agent stumbles into treasure via a weird path
# Advantage at step 0 happens to be HUGE: +15
#
# Actor loss = -log(0.02) * 15 = MASSIVE gradient
#
# This ONE episode completely rewrites the policy.
# Actions that were previously good now have low probability.
# All the learning from episodes 1-200? Destroyed in one update.

Why does this happen?

The policy gradient has no speed limit. If the advantage is big, the update is big. Period. There's nothing stopping a single batch from changing the policy from "go right" to "go left" in one step.

PPO's fix: a speed limit on policy changes

"Learn from this experience, but don't change the policy too much in one step."

Why We Reuse Data — and Why We Can't Just Force the Answer

Problem: sampling is expensive

# Actor-Critic (Ch.4):
# 1. Run episode → collect data
# 2. Compute loss, one gradient step
# 3. THROW AWAY the data
# 4. Run a new episode
#
# For an LLM: generating one response = a full forward pass.
# Throwing it away after one gradient step is wasteful.
# Can we reuse the same batch for multiple gradient steps?

Idea: update, check, update, check...

# Start: p(action) = 0.40, advantage = +2.0
#
# Step 1: gradient pushes p up → p = 0.46
# Step 2: same data, push again → p = 0.51
# Step 3: same data, push again → p = 0.55
# Step 4: same data, push again → p = 0.60
# ...
# When do we stop?? Without a limit, p rockets to 1.0
# based on one batch of data. Same catastrophe as before.

Why not just set p = 0.48 directly?

Tempting: "I know I want p to increase 20%. Just set it there."

But you don't control probabilities directly. You control weights (millions of them), and the probability is the output of a giant nonlinear computation:

# weights → matrix multiplies → activations → more layers → logit → softmax → p
#
# Example: loss = 2y, where y = (x-1)²
# At x=5: y=16. Want y=0? Need x to land at 1.
# Pick lr to "fix" y: lr=8 → x = 5 - 8×16 = -123. Overshot wildly.
#
# The lr that perfectly fixes ONE output sends the weights flying,
# which breaks every OTHER output (probabilities at other states).
#
# Neural networks can only be updated bit by bit.
# You push a little, check how far you went, push again.
# The question is: when to STOP pushing.

PPO's answer: stop when the probability has moved 20% from where you sampled

Measure ratio = new_p / old_p. If it exceeds 1.2 (or drops below 0.8), turn off the gradient for that sample. Keep updating the rest.

The Clip: Positive and Negative Advantages

The rule

# If advantage > 0 (good action): want probability UP
#   → stop when ratio exceeds 1.2 (gone up enough)
#   → but if ratio < 1.0 (went wrong way), keep correcting!
#
# If advantage < 0 (bad action): want probability DOWN
#   → stop when ratio drops below 0.8 (gone down enough)
#   → but if ratio > 1.0 (went wrong way), keep correcting!

The code — one batch of B samples

ratio = new_prob / old_prob   # shape (B,) — how far each sample moved

# Active mask: one-sided clip per sample
active = (
    ((advantage >= 0) & (ratio <= 1.2))
    | ((advantage < 0) & (ratio >= 0.8))
).float()

# Loss: only active samples contribute gradient
loss = -(log(new_prob) * advantage * active).mean()

That's it. Samples that have moved too far in the desired direction get masked out (gradient = 0). Samples that haven't moved enough, or moved the wrong way, keep getting full gradient.

Different samples saturate at different epochs. In a batch of 200 samples, sample 14 might clip at epoch 1, while sample 87 clips at epoch 3. The mask is per-sample — clipped samples contribute zero gradient while others keep learning.

Negative advantage example

# old_prob = 0.50, advantage = -3.0 (bad action)
#
# Epoch 1: ratio = 1.00 → active ✓ → push DOWN → new_prob = 0.43
# Epoch 2: ratio = 0.86 → active ✓ → push DOWN → new_prob = 0.38
# Epoch 3: ratio = 0.76 → ratio < 0.8 → MASKED. Stop punishing.
Why torch.min(unclipped, clipped) gives the same result 
# The standard PPO code you see in papers:
unclipped = ratio * advantage
clipped = torch.clamp(ratio, 0.8, 1.2) * advantage
loss = -torch.min(unclipped, clipped).mean()

# Why is this the same as the active mask?
#
# When adv > 0 and ratio > 1.2:
#   unclipped = ratio * adv (big positive)
#   clipped   = 1.2 * adv   (smaller positive)
#   min picks clipped → a CONSTANT → gradient = 0 ← same as mask!
#
# When adv < 0 and ratio < 0.8:
#   unclipped = ratio * adv (small negative, close to 0)
#   clipped   = 0.8 * adv   (bigger negative)
#   min picks clipped → a CONSTANT → gradient = 0 ← same as mask!
#
# When ratio is in [0.8, 1.2]:
#   clamp does nothing → unclipped = clipped → normal gradient
#
# Same logic, fancier expression. The mask version is clearer.

The Ratio: Fixing Stale Data Across Epochs

The problem: -log(p) gets weaker each epoch

# Sampled at old_prob = 0.40. After 2 epochs, new_prob = 0.55.
#
# loss = -log(new_prob) * advantage * active
#
# gradient of -log(p): (1 - p)
# At epoch 1: p=0.40, gradient = 0.60 (strong)
# At epoch 2: p=0.46, gradient = 0.54 (weaker)
# At epoch 3: p=0.52, gradient = 0.48 (even weaker)
#
# The signal SHRINKS as p grows. But the data came from p=0.40!
# -log(p) acts like you sampled at 0.55. That's wrong.
# Later epochs waste compute pushing with decreasing strength.

Fix: weight by how much you've drifted from sampling time

ratio = (new_prob / old_prob).detach()  # frozen scalar, not differentiable

# At epoch 1: ratio = 0.40/0.40 = 1.0  → weight × 1.0 (no change)
# At epoch 2: ratio = 0.46/0.40 = 1.15 → weight × 1.15 (push harder)
# At epoch 3: ratio = 0.52/0.40 = 1.30 → weight × 1.30 (even harder)
#
# "The further you've drifted from the sampling distribution,
#  the more you need to correct" — until the clip shuts it off.

loss = -(log(new_prob) * ratio * advantage * active).mean()
#                         ^^^^^
# importance weight: corrects for stale data

Simplification: ratio.detach() × -log(p) collapses to just ratio

The gradient (what moves the weights) is the same for both versions:

Loss formula∂loss / ∂p
-log(p) × ratio.detach() × adv ratio.detach() × (1/p) × adv = (p/p_old) × (1/p) × adv = adv / p_old
-(ratio) × adv  (differentiate through ratio) (1/p_old) × adv = adv / p_old

Same gradient → same weight update → same training. The p's cancel.

So instead of loss = -log(p) * ratio.detach() * adv, just write loss = -(ratio) * adv.

Why different loss VALUES are fine

The optimizer never reads the loss number. It only reads the gradient:

loss.backward()      # computes ∂loss/∂weights
optimizer.step()     # moves weights by: w -= lr × gradient

The scalar loss = 2.7 vs loss = 0.003 never enters the weight update. Example:

Formulaloss value (at p=0.46, ratio=1.15, adv=2)gradient on logit
-log(p) × ratio.detach() × adv−1.15 × 0.78 × 2 = −1.791.24
-(ratio) × adv−1.15 × 2 = −2.301.24
-(ratio) × adv + 99999+99996.71.24

Different loss values, identical gradient, identical weight update. The loss is just a recipe whose derivative produces the push you want.

What if you forget the .detach()? The gradient reverses on most tokens.

Worth knowing because it is a silent bug, not a crash. Differentiating through both the ratio and the log leaves a spurious factor:

# detached (correct) — identical to PPO's r*A:
grad = -(p/p_old) * (1-p) * adv

# NOT detached — an extra (ln p + 1) appears:
grad = -(p/p_old) * (1-p) * adv * (ln p + 1)

Gradient on the logit, with p_old = 0.40, adv = 2:

p_newdetached (= PPO)not detachedln(p)+1
0.46−1.2420−0.2776+0.224
0.52−1.2480−0.4319+0.346
0.30−1.0500+0.2142−0.204

Look at the last row: the sign flipped. ln p + 1 turns negative below p = 1/e = 0.368 — so for any token the model is less than 37% sure about, the un-detached version pushes it down when the advantage says push up. Most token probabilities live below 0.368, so this is the common case, not an edge case.

This is also why the standard implementation is -(ratio * adv) with no log at all: there is nothing left to forget to detach.

Final code

ratio = new_prob / old_prob   # NOT detached — we differentiate through it

active = (
    ((advantage >= 0) & (ratio <= 1.2))
    | ((advantage < 0) & (ratio >= 0.8))
).float()

loss = -(ratio * advantage * active).mean()

The clip keeps ratio in [0.8, 1.2], so the correction is at most 20%. The clip does 90% of the work; the ratio makes later epochs push at full strength instead of fading.

The rigorous version: the ratio is not a heuristic, it is an exact identity

Everything above is the intuition — "you drifted, so push harder" — and it is worth keeping. But it makes the ratio sound like a tuning trick that happens to work. It is not. It is forced, and here is the derivation.

Step 1 — state what we actually want. The policy gradient is an average over responses drawn from the current policy:

want:  Ex ~ π_new[ ∇log π_new(x) · advantage ]
              ↑ the subscript matters — ch. 4 of info theory: whoever sits
                under the E is whose samples you are averaging over

have:  samples drawn from π_old, because that is what generated the batch

So we need an average under one distribution, computed from samples of another. That is a solved problem with an exact answer.

Step 2 — the identity (importance sampling), in three lines. Multiply and divide by the thing you did sample from:

Ex~p[ f(x) ]  =  Σ  p(x) · f(x)

               =  Σ  q(x) · p(x)/q(x) · f(x)      # inserted q/q = 1

               =  Ex~q[ p(x)/q(x) · f(x) ]

# No approximation anywhere. This is algebra — true for any q
# that is non-zero wherever p is.

Substituting p = π_new, q = π_old: the factor you must multiply by is π_new/π_old. That is the ratio. It is not chosen — it is the unique reweighting that makes an average over old samples equal an average over new ones.

Step 3 — so restate what was wrong with -log(p) alone. The card at the top said the signal "gets weaker," which is the symptom. The real problem is sharper:

# Without the ratio you are computing:
Ex~π_old[ ∇log π_new(x) · advantage ]

# ...which is the gradient of nothing you asked for. It is not a
# weak estimate of the policy gradient — it is a BIASED one, an
# estimate of the wrong quantity. The ratio makes it unbiased.

"Empirically it works" becomes "it is the only thing that is correct."

Sanity check: the weights average to exactly 1 
# Under the distribution you actually sampled from:
Ex~π_old[ π_new/π_old ]  =  Σ π_old(x) · π_new(x)/π_old(x)
                          =  Σ π_new(x)
                          =  1

So reweighting does not inflate or shrink the total signal — it only redistributes it, moving weight onto the samples the new policy would have produced more often. A good check that nothing is being smuggled in.

Now the information-theory reading, which is the cleanest mental model of all. The ratio is an exponentiated log-difference, and you know what log-differences are: bit counts.

ratio = π_new/π_old = 2^( log₂π_new − log₂π_old )

# And from info theory ch. 1, −log₂p is a code length. So:
log₂π_new − log₂π_old = ( −log₂π_old ) − ( −log₂π_new )
                      = bits the OLD policy spent on this token
                        minus bits the NEW policy spends
                      = how many bits CHEAPER this token became

# So: ratio = 2 ^ (bits saved).  Check it on this page's numbers:
old = 0.40, new = 0.46:  log₂(0.46)−log₂(0.40) = +0.2016 bits → 2^0.2016 = 1.15 ✓
old = 0.40, new = 0.52:  log₂(0.52)−log₂(0.40) = +0.3785 bits → 2^0.3785 = 1.30 ✓

A ratio of 2 means "the new policy describes this token one bit more cheaply." The importance weight is literally how much the model's opinion of this token has changed, measured in bits.

Which turns the clip into a bit budget. Take log₂ of the clip bounds:

clip bound on the ratiosame bound in bitsreads as
1.2 (upper)+0.263 bits"you may not make this token more than 0.26 bits cheaper in one batch"
0.8 (lower)−0.322 bits"...nor more than 0.32 bits more expensive"

And notice something the ratio form hides completely. [0.8, 1.2] looks symmetric. In bits it is not: 0.322 vs 0.263 — the standard clip permits 22% more downward movement than upward. The "symmetric" clip is quietly biased toward suppressing tokens rather than promoting them.

Which is a second, independent argument for chapter 15's Clip-Higher. DAPO motivates ε_high = 0.28 by the headroom available to low-probability tokens; in bits it also simply fixes the asymmetry:

standard  [0.8, 1.20]  →  bits [ −0.322 , +0.263 ]   # 22% biased DOWN
DAPO      [0.8, 1.28]  →  bits [ −0.322 , +0.356 ]   # 11% biased UP

(That bit-symmetry reading is a derivation from this page, not an argument the DAPO paper makes — but the numbers are exact, and they land in the same place.)

Last piece: why bound the ratio at all, given the identity is exact? Because exact and usable are different things. The identity holds for any amount of drift, but the variance of the estimate does not:

# The estimator's variance involves E[ ratio² ]. If π_new and π_old
# drift far apart, a few samples get enormous weights and the
# estimate is dominated by them — unbiased but useless.

clipping ratio ≤ 1.2  ⟹  ratio² ≤ 1.44   # bounded weight ⟹ bounded variance

So the two pieces have cleanly separate jobs, and this is the sentence to remember: the ratio makes the estimate correct; the clip keeps it usable. One is about bias, the other about variance — which is also exactly why the clip is a per-batch speed limit while the KL leash (page 6) bounds total drift.

Epoch-by-epoch: -log(p) alone vs with ratio correction

# ⚠️ IMPORTANT: we track the push on the LOGIT (the raw number before softmax).
# The logit is what the optimizer actually changes. The probability is just
# softmax(logit) — a derived quantity. SGD reads gradients on LOGITS, not on p.
#
# For -log(p): gradient that reaches the logit = (1-p) × adv
# For ratio:   gradient that reaches the logit = ratio × (1-p) × adv

The standard PPO code (what papers and libraries use) 
ratio = torch.exp(new_log_probs - old_log_probs.detach())

unclipped = ratio * advantages
clipped = torch.clamp(ratio, 0.8, 1.2) * advantages
actor_loss = -torch.min(unclipped, clipped).mean()

Change 1: why torch.exp(log_new - log_old) = ratio

# log_new = log(new_prob),  log_old = log(old_prob)
# log_new - log_old = log(new_prob / old_prob)   ← log rule
# exp(log(x)) = x
# so: exp(log_new - log_old) = new_prob / old_prob = ratio
#
# Why bother? Probabilities can be tiny (1e-8). Dividing two tiny
# floats loses precision. Subtracting their logs keeps full precision.

Change 2: why min(unclipped, clipped) = the active mask

Four cases, worked out with numbers:

# CASE 1: adv > 0, ratio INSIDE [0.8, 1.2]  (e.g. ratio=1.1, adv=+2)
#   clamp(1.1, 0.8, 1.2) = 1.1 (unchanged)
#   unclipped = 1.1 × 2 = 2.2
#   clipped   = 1.1 × 2 = 2.2 (same!)
#   min = 2.2 → normal gradient flows. ✓ (same as active=True)

# CASE 2: adv > 0, ratio OVER 1.2  (e.g. ratio=1.5, adv=+2)
#   clamp(1.5, 0.8, 1.2) = 1.2
#   unclipped = 1.5 × 2 = 3.0
#   clipped   = 1.2 × 2 = 2.4
#   min = 2.4 → picks the CONSTANT (1.2×2). Gradient = 0. ✓ (same as active=False)

# CASE 3: adv < 0, ratio INSIDE [0.8, 1.2]  (e.g. ratio=0.9, adv=-3)
#   clamp(0.9, 0.8, 1.2) = 0.9 (unchanged)
#   unclipped = 0.9 × (-3) = -2.7
#   clipped   = 0.9 × (-3) = -2.7 (same!)
#   min = -2.7 → normal gradient flows. ✓ (same as active=True)

# CASE 4: adv < 0, ratio UNDER 0.8  (e.g. ratio=0.6, adv=-3)
#   clamp(0.6, 0.8, 1.2) = 0.8
#   unclipped = 0.6 × (-3) = -1.8
#   clipped   = 0.8 × (-3) = -2.4
#   min picks the SMALLER number: min(-1.8, -2.4) = -2.4
#   -2.4 = 0.8 × adv = CONSTANT → gradient = 0. ✓ (same as active=False)
#
# Key insight for case 4: adv is negative, so BOTH values are negative.
# -1.8 > -2.4 (closer to zero). min picks -2.4 (further from zero).
# That's the clamped one — a constant — so gradient = 0.

RLHF Step 1: Where Does the Reward Come From?

The problem: text has no environment

# Gridworld: the WORLD hands you the reward.
#   step into gold → +10. Step into pit → -10. Rules of the game.
#
# LLM: the model writes "Add more examples to each point."
#   ...and? Nothing happens. No gold, no pit. Text just sits there.
#
# To run ANY of the RL from ch. 3-5, you need a number: reward = ?
# RLHF's answer: BUILD the reward function out of human opinions.

Why comparisons, not scores

# Ask a human: "rate this essay advice 0 to 1"
#   Person 1 says 0.8. Person 2 says 0.5. Same response!
#   Absolute scores are noisy — everyone has a different scale.
#
# Ask instead: "which of these two is better?"
#   Person 1: A. Person 2: A. Consistent!
#   Humans are bad at absolute numbers, good at comparisons.

The preference dataset

# Show a human two responses to the SAME prompt:

prompt = "How do I make my essay longer?"
response_A = "Add more examples and elaboration to each point."
response_B = "Add spaces between every word lol"

# Human clicks: A is better.  → one training pair: (prompt, A ≻ B)
# Collect ~100k of these pairs. That's the entire human input to RLHF.

What the RM actually is — build it in three moves

The RM is not a new network trained from scratch — 100k pairs could never teach a model what text even is. It starts as a copy of the pretrained LLM:

# 1. Copy the SFT LLM — the ENTIRE pretrained transformer body.
#    All of its language understanding comes along for free.
rm_body = copy(sft_llm)          # billions of weights, all pretrained

# 2. Throw away the vocab head (hidden → 50k token scores).
#    Bolt on a fresh one-number head:
rm_head = Linear(4096, 1)        # the ONLY randomly-initialized part

# 3. To score: run the text through, read the head at the LAST token:
h     = rm_body(prompt + response)   # (T, 4096) hidden states
score = rm_head(h[-1])               # one number = RM(prompt, response)

"So it's a regression head?" Structurally yes — trained, no. Regression needs target numbers, and no target scores exist anywhere in the data: nobody ever labeled a response "0.82." The only supervision is "A beat B." So the scalar is trained purely through the pairwise loss below — 0.82 is a value the network settled on, not a label it matched. (This is also why only the GAP between two scores means anything: a head trained only through differences has no absolute scale. Add 100 to every score → same loss.)

And note the output is UNBOUNDED. There is no sigmoid on the head — real RM scores are any real number (−8.3, +4.1, …). The sigmoid appears in the loss, never on the score. The friendly-looking 0.45 / 0.82 used on this page are readable stand-ins, not a 0–1 range; don't read them as probabilities.

Division of labor: pretraining taught it language (trillions of tokens); the pairs teach it only taste (100k comparisons) — a thin judgment layer on top of representations that already understand any text.

Train the reward model on the pairs

Input: (prompt, response). Output: one score — from the network you just built above.

# Before training, the RM's scores are random:
RM(prompt, response_A) = 0.45
RM(prompt, response_B) = 0.52   # wrong order! B scores higher

# Training objective: for every pair, make RM(preferred) > RM(rejected).
# The gradient pushes RM(A) up and RM(B) down. After many epochs:

RM(prompt, response_A) = 0.82   # ✓ preferred scores higher
RM(prompt, response_B) = 0.11
The exact RM loss (Bradley-Terry), with numbers 
# loss = -log( sigmoid( RM(preferred) - RM(rejected) ) )
#
# Before training: RM(A)-RM(B) = 0.45 - 0.52 = -0.07
#   sigmoid(-0.07) = 0.483
#   loss = -log(0.483) = 0.728        ← big loss, wrong order
#
# After training: RM(A)-RM(B) = 0.82 - 0.11 = 0.71
#   sigmoid(0.71) = 0.670
#   loss = -log(0.670) = 0.400        ← smaller loss, right order
#
# Note: only the GAP matters, not the absolute scores. The loss keeps
# shrinking as the gap widens — sigmoid never quite reaches 1.

Both of those properties — only-gaps-matter, and a loss that never stops shrinking — are built into the statistical model this loss comes from. For it derived from scratch (plus its link to Elo and arena leaderboards), see the optional aside The Bradley-Terry model.

How that loss becomes a trained RM — then a frozen grader

The card above jumped from 0.45/0.52 to 0.82/0.11 with just "after many epochs." Here is the machinery in that gap — and it is nothing new. Training the RM is ordinary supervised learning: the same backward() / step() from chapters 3–5. No ratio, no clip, no advantage — those come later, for the LLM, not for the RM.

# --- ONE pair, ONE step (weights = the RM's, right now) ---
loss = -log(sigmoid(RM(A) - RM(B)))   # = 0.728  (from the foldable)
loss.backward()      # every RM weight gets a gradient
optimizer.step()    # nudge weights to shrink THIS pair's loss

# One step moves the two scores a hair in the right direction:
#   RM(A): 0.45 → ~0.47   (up)      loss: 0.728 → ~0.70
#   RM(B): 0.52 → ~0.50   (down)   (illustrative — one SGD step is tiny)

# --- The loop: repeat that over the whole dataset ---
for epoch in range(few):
    for (prompt, A, B) in preference_pairs:   # all ~100k
        loss = -log(sigmoid(RM(prompt,A) - RM(prompt,B)))
        loss.backward(); optimizer.step(); optimizer.zero_grad()

# Those accumulated nudges ARE what turns 0.45/0.52 into the
# 0.82/0.11 shown above. The "after" scores are this loop's end state,
# not a separate magic step.

Then the crucial move — freeze it:

RM.requires_grad_(False)   # no more gradients
RM.eval()                   # it never learns again

# From now on RM is a fixed, pure function:  score = RM(prompt, response)

That frozen function is the answer to page 5's reward = ?. On the next page the LLM trains with PPO against this stationary grader — the RM plays the role the gridworld's "+10 gold / −10 pit" played. Two separate trainings, in order: (1) train the RM with plain SGD (this page), (2) then train the LLM with PPO against the frozen RM (next page). Don't merge them.

"But doesn't the next pair UNDO this one?" — the tug-of-war on B

Say the dataset has A ≻ B and B ≻ C. Train on (A,B): push RM(A) up, RM(B) down. Then train on (B,C): push RM(B) up, RM(C) down. B just went back up — did the second pair undo the first? Does this ping-pong forever, with A and B ending up close together again?

It would — if the push were constant size. It isn't. The push fades with the pair's own gap. Watch it on a pretend-RM that is just three raw numbers:

scores = {A: 0.0, B: 0.0, C: 0.0}   # one number per response
pairs  = [(A,B), (B,C)]              # A beat B; B beat C
lr = 1.0                               # huge on purpose, to see the motion

for round in range(4):
    for (w, l) in pairs:               # one pair at a time (your scenario)
        gap  = scores[w] - scores[l]
        push = 1 - sigmoid(gap)         # ← THE FADE: gradient of -log(sigmoid(gap))
        scores[w] += lr * push          #   big gap → tiny push, small gap → big push
        scores[l] -= lr * push

3: (A,B)0.770.315+1.22−0.18−1.04
3: (B,C)0.860.298+1.22+0.11−1.34
4: (A,B)1.110.248+1.47−0.13−1.34
4: (B,C)1.200.231+1.47+0.10−1.57

Read the table three ways:

  • Yes, the tugs fight — that's the mechanism, not a bug. B gets shoved down 0.50, then up 0.62 (row 2: "B is up again!"). But look at B's swing: 0.62 → 0.42 → 0.30 → 0.23. It shrinks every round.
  • The fade is the stabilizer. Each pair only pushes as hard as its own gap is unfinished. B ends parked (~+0.1) between A (+1.47) and C (−1.57): a staircase A > B > C, which satisfies BOTH pairs at once. A and C run away because each has only ONE tug; B stays middle because it has two opposing ones.
  • B can never rejoin A. This is the key self-balancing move: if B ever creeps toward A, the (A,B) gap shrinks — which makes the (A,B) down-push on B stronger. Approaching A reactivates the exact force that separates them. Whichever gap is currently smallest gets the loudest correction.
"A hit +1.47 — scores can go past 1? Is there a guard?"

Is the SCORE bounded? No, deliberately. The head is a bare Linear(4096, 1); the sigmoid is in the loss, not on the output. +1.47 is normal — and since only gaps matter (add 100 to every score → identical loss), the absolute scale is arbitrary anyway.

Can the PUSH exceed 1? Never. push = 1 − σ(gap) ∈ (0,1) by construction — at most 1.0 when the model has the pair completely backwards, → 0 when it's confident. One update moves a score by at most lr × 1. (The step is lr × push, so a too-large lr still overshoots; within one pair that can't reverse the order — the gap strictly increases — but with shared weights it wrecks OTHER pairs. Page 0's crash, again.)

Does it grow forever, then? Yes — logarithmically.

# one pair, lr = 1. Each update: A += push, B -= push, so gap += 2·push
#   gap: 0 → 1.00 → 1.54 → 1.89 → 2.15 → 2.36 → ...
# each step adds 2·lr·(1−σ(gap)), which decays like e^(−gap),
# so the gap grows like ln(t). Reaching gap 10 takes ~11,000 updates.
# Unbounded — but it cannot explode on its own.

# The literal guard in code:
loss.backward()
clip_grad_norm_(rm.parameters(), 1.0)   # cap the update size
optimizer.step()
# plus: small lr, weight decay, and the real stopper — early stop ~1 epoch.
# DPO's equivalents: β scales the gap, the frozen reference anchors it.
In real training it's even cleaner: batches make the tugs cancel INSIDE one update 
# Real training doesn't alternate pair-by-pair. Both pairs sit in one
# batch; gradients are computed from the SAME scores, then summed:

# round 1, batch = {(A,B), (B,C)}, all scores 0.0:
#   (A,B): gap 0 → push 0.5:   A +0.5,  B −0.5
#   (B,C): gap 0 → push 0.5:   B +0.5,  C −0.5
#   summed:                    A +0.5,  B −0.5+0.5 = 0,  C −0.5

# B's two tugs cancel ARITHMETICALLY before the weights ever move.
# B never wiggles at all — A and C just separate symmetrically
# around it: pushes 0.50, 0.38, 0.29, ... same fade, no ping-pong.
And when the data DISAGREES (A ≻ B, B ≻ C, C ≻ A) — the ceiling, explained 
# Raters produce a cycle: A beat B, B beat C, C beat A. No staircase
# can satisfy all three. What does the loop do? Batch it:

#   (A,B): A +0.5, B −0.5
#   (B,C): B +0.5, C −0.5
#   (C,A): C +0.5, A −0.5
#   summed: A 0, B 0, C 0    ← every letter wins once, loses once

# Scores freeze at equal → every gap 0 → sigmoid 0.5 → the RM predicts
# a coin flip on these pairs forever. loss stuck at -log(0.5) = 0.693.
# These pairs are UNLEARNABLE — and real preference data is full of
# them, because humans genuinely disagree. That is the 65-75% accuracy
# ceiling in the next card, derived instead of asserted. Training more
# epochs can't resolve a cycle — it can only memorize which exact pairs
# appeared, i.e. overfit.

So when does the loop stop? (the gate you noticed is missing)

Good catch: that loop has no natural stop. sigmoid never reaches 1, so the loss shrinks toward zero forever as the gap widens — "train to convergence" would just mean "train until it memorizes." The RM is one of the rare models you deliberately undertrain. The real gate is not the loss and not a fixed epoch count you guess in advance; it's held-out preference accuracy:

# Split the pairs BEFORE training:
train_pairs, val_pairs = split(preference_pairs)   # e.g. 95% / 5%

# After each pass, measure on pairs the RM has NEVER seen:
val_acc = mean( RM(prompt,A) > RM(prompt,B)  for pair in val_pairs )
#   "on unseen pairs, how often does the winner outscore the loser?"

# Stop when val_acc stops improving. In practice that is ~1 epoch:
#   epoch 1:  train_loss 0.69 → 0.55,  val_acc 0.50 → 0.71   ✓ keep
#   epoch 2:  train_loss 0.55 → 0.38,  val_acc 0.71 → 0.69   ✗ OVERFIT
#             (train loss still dropping, but val_acc went DOWN — stop)

That accuracy tops out around 65–75%, not 99% — because it is capped by how often two humans even agree on the same pair. The RM cannot be more right than its labels. (Numbers above are illustrative of the shape; the ~1-epoch and 65–75% figures are the reported industry norm since InstructGPT.)

Undertraining on purpose is only the first of the reward model's failure modes. The other three — correlated pairs, length bias, and reward over-optimization — need the PPO loop and the KL leash before they make sense, so they get their own tab at the end: 7. What Breaks.

What you now have

An automatic grader: a function that scores ANY response to ANY prompt, no human in the loop. It's the "+10 gold / −10 pit" of the text world — except it's learned, not given. That difference will bite us on the last page (reward hacking).

"ANY response"? It only ever saw 100k pairs — can it judge text that looks nothing like them?

Fair challenge. Split it in two:

Different phrasing — fine. The RM's body is the whole pretrained LLM, so a response worded unlike any training pair still lands in representations it understands. The pairs taught taste, not language; taste generalizes across phrasings the way all LLM finetuning does.

Different distribution — genuinely not fine. The pairs were collected on responses sampled from the SFT model. During PPO the policy drifts away from that distribution — and the RM is now queried on text unlike anything its preference data covered. It still confidently outputs scores; they're just unsupported. Worse, the policy is actively hunting for high scores, so it steers into exactly these blind regions. That is the reward hacking / over-optimization from the trap table, met from a new angle.

Two production answers: (1) the KL leash (two pages ahead) — keep the policy near the reference, i.e. inside the region the RM's training data actually covers; (2) iterated RLHF — periodically collect fresh preference pairs on the current policy's outputs and retrain the RM, so the grader's coverage follows the student (InstructGPT and Anthropic both did this).

RLHF Step 2: PPO, With the LLM as the Policy

The mapping — same algorithm, different world

Note the reward row: like the gridworld's gold, the score arrives only when the episode ends. No per-token rewards — the RM can't grade half a sentence.

One episode, traced end to end

# 1. Sample a prompt from the dataset
prompt = "How do I make my essay longer?"

# 2. The LLM (current policy) generates a response, token by token,
#    sampling from its softmax at each step — exactly like sampling
#    up/down/left/right in the grid
response = "Add more examples and elaboration to each point."
#    (also save old_prob of every generated token — PPO needs them)

# 3. The frozen RM grades the finished response
reward = RM(prompt, response) = 0.82

The advantage — same formula as chapter 4

# The critic V is a small extra head ON the LLM. Input: the prompt.
# Output: one number — "for this prompt, what RM score do I usually get?"

V(prompt) = 0.60   # "essay questions: I typically score ~0.60"

# Advantage = actual − expected. Chapter 4, unchanged:
advantage = 0.82 - 0.60 = +0.22   # better than expected → push up

# A second sampled response scores badly:
#   RM = 0.11 → advantage = 0.11 - 0.60 = -0.49 → push down
#
# Why V matters here (same as ch.4): hard prompts get low RM scores
# for EVERY response. Without V, every response to a hard prompt gets
# punished — even the best one the model can currently produce.

One reward, many tokens

# The response has ~10 tokens. The RM gave ONE number for all of them.
# Simplest scheme: every token inherits the response's advantage.

#   token:      "Add"  "more"  "examples"  ...  "point"  "."
#   advantage:  +0.22  +0.22   +0.22       ...  +0.22    +0.22

# Then each token is one PPO sample: it has its own old_prob (saved at
# generation), its own new_prob, its own ratio, its own clip check.
# The pages 1-3 machinery runs per token, unchanged:

ratio  = new_prob / old_prob          # per token, shape (T,)
active = ((adv >= 0) & (ratio <= 1.2)) | ((adv < 0) & (ratio >= 0.8))
loss   = -(ratio * adv * active).mean()

# (Smearing one grade over all tokens is crude — "was every word of a
#  0.82 response equally good?" No. Chapter 8 shows GRPO doing the same
#  broadcast, and ch. 11 shows the fix: per-token teacher feedback.)

Shapes: how one response becomes a (batch, tokens) tensor

Above, one response gave tensors of shape (T,). Real training uses (batch, T). Walk the chain — the batch dimension changes meaning on the way from the grid to the LLM:

# (1) GRID (ch. 3-4): one sample = one STEP of the route.
#     Walking is sequential (need step 3's state before acting step 4),
#     but once the route is RECORDED, all stored states go through the
#     net in one forward pass:
states  # (T, 9)  T steps, each a one-hot grid position
logits  # (T, 4)  each row: that step's up/down/left/right probs
#     Batch = a pile of step-rows. No token dimension anywhere.

# (2) LLM: one sample = one TOKEN. So a 3-token answer = 3 rows?
#     Row t would be (state = the prefix, action = the token):
#       feed "Q"          → prob of "Add"
#       feed "Q Add"      → prob of "more"
#       feed "Q Add more" → prob of "examples"
#     Legal, but wasteful — the three prefixes are 90% the same text.

# (3) The causal mask collapses the 3 rows into 1. One forward pass on
#     the FULL sentence: position t is only allowed to look left, so its
#     output IS p(token_t | prefix_t) — for every t simultaneously:
logits = llm("Q Add more examples")   # (T, vocab) — all probs, one pass
#     The grid net can't do this: its states share no structure. The
#     causal mask is exactly what turns token ROWS into a token DIMENSION.

# (4) That frees the batch dimension for whole sentences. Stack 32
#     responses, pad the short ones:
tokens    # (32, 64)  64 = longest response; shorter rows right-padded
pad_mask  # (32, 64)  1 = real token, 0 = padding (excluded from the loss)

# (5) Each row is self-contained: its own old_log_probs, its own
#     broadcast advantage, its own mask. Nothing in the loss looks
#     ACROSS rows — so rows from different prompts mix freely.
#     Collect 100 prompts × 5 responses = 500 rows, shuffle, slice
#     off whatever fits in GPU memory. Which question a row came from
#     is irrelevant; the only unbreakable unit is that a response's
#     tokens stay together in ONE row — computing each token's prob
#     needs its prefix sitting to its left.

(No KV-cache anywhere in this forward — caching past keys/values is a generation trick for producing one token at a time. The training pass is one parallel sweep.)

The full loop — every shape printed

# ---- COLLECT (no_grad; the policy that samples here is "old") ----
prompts   = sample_prompts(100)
responses = llm.generate(prompts, k=5)     # 500 sequences, pad to T=64

tokens        # (500, 64)  token ids
pad_mask      # (500, 64)  1 = real, 0 = padding
old_log_probs # (500, 64)  log p_old(token_t | prefix), saved at generation

rewards = RM(prompts, responses)            # (500,)  one grade per response
values  = V(prompts)                        # (500,)  expected grade per prompt
adv = (rewards - values)[:, None]           # (500, 1) → broadcasts to (500, 64):
                                            # every token gets its response's grade

# ---- TRAIN ----
for epoch in range(4):                        # reuse the batch (page 1!)
    for rows in shuffle(500).split(32):      # NOTE: rows = RESPONSES, not tokens.
                                             # 32 integers in [0,500). Never a token
                                             # index — a token needs its prefix, so a
                                             # response cannot be split (see above).

        # the model emits a distribution over the WHOLE vocab per position...
        logits = llm(tokens[rows])           # (32, 64, 50000)  one causal forward

        # ...and we keep only the log-prob of the token that WAS produced:
        new_log_probs = gather_logprob(logits, tokens[rows])   # (32, 64)
        #   element [i, t] = log p( token t of response i | its prefix )
        #   PER TOKEN — not one number per response. That distinction is
        #   the whole reason PPO can clip each token separately.

        ratio  = torch.exp(new_log_probs - old_log_probs[rows])  # (32, 64)
        active = (((adv[rows] >= 0) & (ratio <= 1.2)) |
                  ((adv[rows] <  0) & (ratio >= 0.8))).float()  # (32, 64)
        loss = -(ratio * adv[rows] * active * pad_mask[rows]).sum() \
                 / pad_mask[rows].sum()     # divide by REAL-token count,
                                             # not 32×64 — padding must not
                                             # dilute the update
        loss.backward(); opt.step(); opt.zero_grad()

critic_loss = ((values - rewards)**2).mean()  # critic learns to predict RM
update_critic()

Per-token or per-response? One .sum() apart — and it separates PPO from DPO

The forward pass above produces a per-token tensor. The number chapter 6 calls "the probability of a whole response" is that same tensor summed along the token axis. Both live one line apart:

new_log_probs                                # (32, 64)  per TOKEN
(new_log_probs * pad_mask[rows]).sum(dim=1)   # (32,)     per RESPONSE
#                                    ↑ mask first, or padding joins the sum
MethodUsesBecause its loss compares…
PPO (this page), GRPOthe per-token tensor, unsummed…each token against its own old probability, so every token needs its own ratio and its own clip decision
DPO, SimPOthe summed per-response number…one whole response against another whole response, so it needs a single score per response

So PPO’s refusal to take that sum is not an oversight — it is what buys per-token clipping. And ch. 6’s Step 0 (product of token probabilities = sum of their logs) is literally this .sum(dim=1).

RLHF Step 3: The Reward Is Fake — Keep a Leash On

Reward hacking: optimizing the grader, not the goal

# The RM is NOT the truth. It's a model of human taste, trained on
# ~100k pairs. It has blind spots. PPO will FIND them.
#
# Example: in the preference data, longer answers happened to win more
# often. The RM quietly learned "long ≈ good". PPO discovers this:
#
#   response: 800 words of fluent, polite, empty padding
#   RM score: 0.95        ← the grader loves it
#   real human: 0.2       ← a person would hate it
#
# PPO doesn't know the 0.95 is a bug. Reward is reward. It will push
# the whole model toward padding — and DESTROY its pretrained abilities
# in the process. This is called reward hacking.

The fix: penalize drifting from the reference model

# π_ref = a FROZEN copy of the LLM before RL started.
# Per token, measure how much the policy's probabilities have drifted
# from the reference (KL divergence — big = drifted far).

reward = RM(prompt, response) - β * KL(π_new || π_ref)

# β = 0.02 (small). Honest vs hacked, with numbers:
#
# honest response: RM = 0.82, KL = 0.3  (normal drift)
#   reward = 0.82 - 0.02 × 0.3  = 0.82 - 0.006 = 0.814   ← barely touched
#
# hacked response: RM = 0.95, KL = 25   (padding gibberish = huge drift —
#   the pretrained model would NEVER produce this, so π_new ≫ π_ref)
#   reward = 0.95 - 0.02 × 25   = 0.95 - 0.50  = 0.45    ← hack wiped out
#
# 0.814 > 0.45: the honest response now wins. The hack isn't worth it.

Wait — isn't the clip already a leash? Why two?

The clip (pages 2-3)The KL penalty
Limitschange per batchtotal drift from π_ref, ever
Compares againstπ_old (re-snapshotted every batch)π_ref (frozen forever)
Analogyspeed limit"stay within 50 km of home"

A thousand small clipped steps, each legal, can still walk the model arbitrarily far from its pretrained self. The clip can't see that — its reference point moves every batch. The KL penalty's reference point never moves, so accumulated drift always costs.

The complete RLHF pipeline

# Stage 1 — SFT: fine-tune pretrained LLM on good demonstrations
#            (this becomes π_ref, the frozen reference)
# Stage 2 — RM: collect ~100k preference pairs, train the reward model
# Stage 3 — PPO: the page-5 loop, with reward = RM - β×KL
#
# That's ChatGPT's original recipe (InstructGPT, 2022).
# Everything in it, you now know piece by piece.

What Breaks: The Reward Model’s Four Failure Modes

The spine: traps in the order the RM’s life produces them

StageWhat goes wrongYou feel it as
1. Collect the pairsCorrelated pairs — one prompt contributes many non-independent comparisonsRM memorizes prompts; wasted compute
1. Collect the pairsLength bias — "longer" is the easiest signal in the dataNothing yet — it detonates in stage 3
2. Train the RMOverfitting — no stop gate, tiny signal, huge modelVal accuracy turns down after ~1 epoch
3. Run PPO against itOver-optimization — the policy hunts the RM’s blind spotsRM score climbing while quality drops

Traps 1 and 3 are planted at data-collection time but only explode later. That delay is what makes them hard: by the time you see padding in the outputs, the cause is 100k labels ago.

Trap 1 — Overfitting: why you deliberately undertrain

Step 1. What "overfit" means here specifically. Not the vague "memorizes training data." Concretely: instead of learning taste ("thorough, correct, on-topic answers win"), the RM latches onto surface marks unique to these exact texts — this labeler’s phrasings, this prompt’s topic words — and uses them to recall which response won.

Step 2. Why the RM is unusually fragile. Count the actual supervision:

# One preference pair teaches exactly ONE BIT: "A won, not B."
#   100,000 pairs = 100,000 bits = 12.5 KILOBYTES of information.
#
# That 12.5 KB is shaping a network with BILLIONS of parameters.
# Compare pretraining: trillions of tokens, each teaching ~a full
# token-prediction target.
#
# A model that big can fit 12.5 KB of labels perfectly, many times
# over, without learning anything general. Memorization is the EASY
# path here, not the hard one.

Step 3. The symptom. (Same numbers as page 4, restated as the diagnosis:)

#   epoch 1:  train_loss 0.69 -> 0.55,  val_acc 0.50 -> 0.71   keep
#   epoch 2:  train_loss 0.55 -> 0.38,  val_acc 0.71 -> 0.69   OVERFIT
#
# Note the two columns disagree. Train loss says "still improving!"
# Val accuracy says "you are getting worse at the actual job."

Step 4. Why the loss cannot be your gate. This is the tug-of-war result from page 4: the loss keeps shrinking as the gap widens, forever, because sigmoid never reaches 1. A falling train loss is therefore zero evidence of progress — it falls just as happily when the model is memorizing. There is no loss value that means "done."

Step 5. So the gate is held-out accuracy — and it plateaus almost immediately:

val_acc = mean( RM(prompt,A) > RM(prompt,B)  for pair in val_pairs )
# Stop when this stops rising. In practice: ~1 epoch. Sometimes 2.

Step 6. And it tops out at 65–75%, not 99% — which page 4 derived rather than asserted: when labelers disagree, the pairs form cycles (A≻B, B≻C, C≻A) whose gradients cancel exactly, freezing those scores at a coin flip forever. Those pairs are unlearnable. More epochs cannot resolve a contradiction — they can only memorize which contradictory pairs appeared, which is precisely the overfitting in step 1.

Step 7. Practical settings, and why each one:

SettingTypicalWhy
epochs1 (sometimes 2)Val accuracy peaks there
learning rate~1e−5 or lowerBig steps memorize individual pairs before the shared pattern emerges
what you watchval accuracyThe loss is uninformative (step 4)

Trap 2 — Correlated pairs: one prompt sneaking in six times

Step 1. Where multiple pairs per prompt come from. You do not show a labeler two responses. You show K responses to one prompt and ask them to rank all K. Ranking 4 costs barely more labeler time than comparing 2, and yields far more comparisons — that is the whole point.

Step 2. One ranking becomes C(K,2) pairs. With K=4 and the labeler ranking c1 > c2 > c3 > c4:

# every response beats every response below it:
(c1,c2) (c1,c3) (c1,c4) (c2,c3) (c2,c4) (c3,c4)
# C(4,2) = 6 pairs from ONE prompt and ONE labeler judgment.

Step 3. The naive move — treat those 6 as 6 ordinary training examples and shuffle them into the dataset like everything else. This is what breaks.

Step 4. Why it breaks, reason A (statistical). Those 6 pairs are not independent samples. They encode ONE labeler’s ONE opinion about ONE prompt. Shuffled apart, that single opinion now steers 6 separate weight updates per epoch:

# If this labeler had an idiosyncratic view of this prompt, the RM
# gets told the same quirk 6 times, from 6 different directions.
# It looks like 6 pieces of evidence. It is 1.
# -> the RM memorizes THIS prompt's ranking. Trap 1, accelerated.

Step 5. Why it breaks, reason B (compute). Count forward passes. Each of the 4 responses appears in 3 of the 6 pairs (it pairs with each of the other three):

# SHUFFLED: 6 pairs x 2 responses = 12 forward passes
#           ...but there are only 4 distinct texts. Each is
#           recomputed 3 times, in 3 different batches. 3x waste.

Step 6. The fix — keep the ranking together in one batch (this is what InstructGPT does). Score each response once, then form all 6 comparisons from those 4 numbers:

# 4 forward passes, one per distinct response:
s1, s2, s3, s4 = RM(prompt, c1), RM(prompt, c2), RM(prompt, c3), RM(prompt, c4)

# all 6 comparisons reuse those 4 numbers — no extra forwards:
loss = mean( -log(sigmoid(s_w - s_l))  for (w,l) in six_pairs )
loss.backward(); optimizer.step()

# RESULT: 4 forwards instead of 12, and ONE grouped weight update
# per prompt instead of 6 — so the prompt counts once, as it should.

Both problems are fixed by the same move, which is why this is a favorite question: the grouping is simultaneously the statistical fix and the 3× speedup.

Trap 3 — Length bias: the easiest feature wins

Step 1. The bias is not a labeling error. This is the part people get wrong. Given two answers, the more thorough one usually is better. So "longer wins" is a genuine, honest correlation in the data — the labelers were not being lazy.

Step 2. Why the RM over-learns it. Gradient descent takes the cheapest route that lowers the loss. Compare what two features cost the network:

FeatureWhat computing it requires
"Is this answer helpful and correct?"Read it, understand the question, judge the reasoning — the full depth of the network
"How long is it?"Essentially count tokens. Nearly free.

Both lower the loss on the training pairs. One is nearly free. So the RM leans on length far more than the correlation justifies: it learns score ≈ partly f(length).

Step 3. Nothing looks wrong yet. Val accuracy is fine — length genuinely predicts the labels on held-out pairs too. Trap 3 is invisible at RM-training time. It detonates only in stage 3.

Step 4. PPO finds it. The policy is searching for high RM scores, and "add more words" is the cheapest direction that raises the score. That is exactly page 6’s example, now with its origin explained:

#   response: 800 words of fluent, polite, empty padding
#   RM score:   0.95    ← the grader loves it (length!)
#   real human: 0.2     ← a person would hate it

Step 5. Detect it before it costs you a run — the diagnostic is one line:

# On a FIXED eval set (not the training pairs):
corr( RM(x, y),  len(y) )     # ideally ~0; often strongly positive

# Sharper version: hold quality fixed and vary only length.
# If padding a good answer with filler RAISES its score, you have it.

Step 6. Three places to fix it, in increasing order of bluntness:

WhereFix
Data collectionLength-balance the pairs: make sure the winner is short about as often as it is long, so length stops predicting the label
PPO rewardreward = RM(x,y) − λ × len(y) — an explicit penalty that cancels the RM’s bias
The score itselfNormalize by length — this is what chapter 6’s SimPO does to the DPO score, for exactly this reason

Trap 4 — Reward over-optimization: even a GOOD reward model fails

Step 1. Two different scores exist, and only one is trainable. Name them, because the whole trap lives in the gap between them:

NameWhat it isAvailability
proxyThe RM’s scoreFree, instant, on every response — so you train on it
goldWhat real humans actually thinkExpensive, slow — you can only sample it occasionally

Step 2. The finding (Gao et al., 2023). Train PPO against the proxy while periodically measuring gold with fresh human labels. Gold does not track proxy — it rises, peaks, then declines while proxy keeps climbing:

# PPO steps        proxy (RM score)      gold (true quality)
#   early              0.60                  0.60
#   mid                0.85                  0.72   ← both rising: healthy
#   late               0.95                  0.55   ← proxy UP, gold DOWN
#
# (Shape is the paper's result; these numbers are illustrative.)
# Every metric on your dashboard says the run is going great.

Step 3. Why — and this is the mechanism, not just "Goodhart’s law". Three links:

# (a) The RM was trained on responses from the SFT model. Its scores
#     are only trustworthy on text that LOOKS like that.
#
# (b) PPO moves the policy AWAY from the SFT distribution — that is
#     literally its job. So the RM is increasingly asked to grade text
#     unlike anything in its training data, where it extrapolates.
#
# (c) The policy is not sampling those regions at random. It is
#     SEARCHING for whatever scores highest — i.e. actively hunting
#     the RM's largest over-estimates. The errors are not noise;
#     they are the target.

Step 4. It is trap 1’s "no stop gate," one level up. The RM’s loss never says "done"; now the policy’s objective never says "done" either. Optimizing harder always raises the proxy. Nothing in the objective knows the proxy has stopped meaning anything.

Step 5. Three fixes, stacked in practice — note none of them is "make a better RM," because the trap survives a good RM:

FixHow it stops the mechanism
KL leash (page 6)Attacks link (b): keeps the policy near π_ref, i.e. inside the region where the RM’s training data actually lives
Early stop on a gold evalAttacks step 2 directly: pay for a small batch of fresh human labels periodically, and stop at the gold peak rather than the proxy peak
Iterated RLHFAttacks link (a): re-collect preference pairs on the CURRENT policy’s outputs and retrain the RM, so its coverage follows the policy instead of falling behind

The KL leash is the one you can implement today with no extra humans, which is why page 6 taught it as the fix. But it only buys distance, not correctness: crank the KL budget up and the peak returns.
