Chapter 14: SimPO

Read after chapter 6. DPO optimizes one quantity and then you generate with a different one. SimPO makes them the same quantity — and deletes the reference model on the way.

The Bug: You Train on One Score and Generate With Another

Step 1 — what chapter 6 optimized

DPO's implicit reward, the one earned on ch. 6 tab 2.2:

r_DPO(x, y) = β × log( P_current(y|x) / P_ref(y|x) )
 
// Two properties to hold on to:
// (a) it is a TOTAL over the response, not a per-token average
// (b) it is measured RELATIVE to a frozen reference model

Step 2 — what you actually rank with at generation time

Now look at what the model does when it produces or scores text. Any time you compare candidate outputs — beam search, best-of-n, ranking two samples — you do not use the raw product of token probabilities, because that punishes long sequences automatically (each extra token multiplies in another number below 1, exactly as ch. 6’s Step 0 showed). You use the average log-probability per token:

p_θ(y|x) = ( 1 / |y| ) × log P(y|x) // |y| = number of tokens
 
// Note what is NOT in this expression:
// - no reference model (there is only one model at inference)
// - and it IS divided by length

So the training objective and the generation metric differ on both properties from step 1. They are simply different functions of the same response.

Step 3 — so they can disagree. Here is the smallest case where they do

Two responses to one prompt. Forget the reference for a moment and just compare total vs average log-probability:

responsetokens |y|total log Paverage log P = total / |y|
winner (thorough)5−3.5−0.70
loser (short, bland)2−2.0−1.00
// Rank by TOTAL log P (what an unnormalized loss pushes on):
−2.0 > −3.5 → the LOSER ranks higher // wrong!
 
// Rank by AVERAGE log P (what generation actually uses):
−0.70 > −1.00 → the WINNER ranks higher // correct

The two rankings point opposite ways, and nothing is broken or unusual here — the loser is just shorter. Length alone flipped the verdict.

Step 4 — how often does this actually happen? The paper measured it

Take a trained DPO model and, for each training triple (prompt, winner, loser), check whether the two rankings agree:

// Does r_DPO(winner) > r_DPO(loser)
// imply avg_logP(winner) > avg_logP(loser) ?
 
agreement on training triples: ~50% // SimPO paper, Meng et al. 2024

About a coin flip. So on roughly half the data, DPO successfully raised the quantity it optimizes while the quantity you generate with went the other way. The training signal and the deployed behavior are only loosely coupled.

SimPO changes DPO in three places, and each one is a separate tab from here:

Fix 1 — Divide by the Number of Tokens

The edit itself

// DPO's score for one response:
score(y) = β × log( P_cur(y) / P_ref(y) )
 
// SimPO's score for one response — length-normalized:
score(y) = ( β / |y| ) × log P_cur(y)
 
// |y| = token count of that response. Note it is the response's OWN
// length — winner and loser are each divided by their own count.

Why dividing is the right move, in one line of arithmetic

Chapter 6 Step 0 established that a response’s probability is a product over tokens, so its log is a sum:

log P(y) = log p(t₁) + log p(t₂) + ... + log p(t|y|) // |y| terms
 
// Every term is negative (probabilities are below 1). So a longer
// response has a more negative sum FOR FREE — not because it is
// worse, but because it has more terms.
 
// Dividing by |y| turns a SUM into a MEAN: "how confident is this
// model per token", which no longer grows with length.

Run the page-0 example through it

Same two responses, now with SimPO’s score at β = 2.0:

response|y|log Pavg = log P / |y|score = β × avg
winner5−3.5−0.70−1.40
loser2−2.0−1.00−2.00
gap = score(winner) − score(loser)
= −1.40 − (−2.00) = +0.60 // winner ahead ✓
 
// Under the unnormalized version the gap was −3.5 − (−2.0) = −1.5,
// i.e. the loser was ahead. Normalizing flipped it to the truth.

The second thing this buys: it removes the length incentive

Chapter 5 tab 7 (trap 3) and ch. 6’s gotcha card both ended at the same place — preference training tends to inflate length. Watch what normalization does to that incentive:

// Suppose the model pads the winner with 5 filler tokens, each with
// a typical log-prob of −0.70 (i.e. exactly average, no better):
 
before: log P = −3.5, |y| = 5 → avg = −0.70
after: log P = −7.0, |y| = 10 → avg = −0.70 // unchanged!
 
// Padding with average-quality tokens moves the score NOT AT ALL.
// To raise an average you must add tokens BETTER than your current
// average — length by itself buys nothing.

Reported effect: the paper finds SimPO does not meaningfully inflate output length — its Gemma-2-9B model averages 1833 tokens against GPT-4-Turbo’s 1802 on the same benchmark, so the win is not bought with verbosity.

Fix 2 — Drop π_ref Entirely

Careful: chapter 6 spent a whole tab justifying the reference. What changed?

This is the step that should make you suspicious, so walk it slowly. Ch. 6 tab 2.1 introduced the reference for one specific job: raw probabilities are not comparable across responses, because a long or unusual sentence has a small probability regardless of quality. Dividing by P_ref fixed that by comparing each response against itself, so length and base-rate cancelled.

But fix 1 already solved that problem a different way. Length normalization makes the score comparable across responses directly. The reference’s main job is now done by the / |y|.

What the two approaches are each doing

DPO's answerSimPO's answer
Make scores comparabledivide by the same response's reference probabilitydivide by the response's token count
Models in memory during training2 (policy + frozen reference)1 (policy only)
Forward passes per pair4 (2 responses × 2 models)2 (2 responses × 1 model)
Matches the generation metric?no — reference appears nowhere at inferenceyes — identical quantity

The compute and memory saving is real and immediate: the reference model is the same size as the policy, so you free roughly half the model memory and half the forward work.

The honest cost — what you give up

The reference had a second job that fix 1 does not replace: it was the anchor. Ch. 6 tab 3 showed β and the frozen π_ref together forming the total-drift leash — chapter 5’s KL leash in DPO clothing. Delete the reference and that explicit guarantee goes with it:

// DPO: the loss itself contains a term that grows when the
// policy moves away from the frozen snapshot.
 
// SimPO: no such term exists. Nothing in the objective knows
// or cares how far you have travelled from the SFT model.

What holds it together in practice is everything around the loss: you start from a good SFT model, train roughly one pass over a fixed preference set with a small learning rate, and the target margin from the next tab keeps the push from running away. That is weaker than a guarantee, and it is the main thing to say out loud if you are asked to compare the two.

Fix 3 — Demand a Margin, Not Just a Win

The problem γ solves: "barely ahead" already satisfies the loss

Every preference loss so far — ch. 5’s Bradley-Terry, ch. 6’s DPO — is happy the moment the gap turns positive, and then keeps pushing with an ever-weaker force. Recall the push from ch. 6:

push = 1 − sigmoid(gap)
 
gap = +0.05 → sigmoid = 0.512 → push = 0.488 // still strong
gap = +0.60 → sigmoid = 0.646 → push = 0.354
gap = +3.00 → sigmoid = 0.953 → push = 0.047 // nearly done

The trouble is that a gap of +0.05 is noise. The model ranks the winner a hair above the loser; one different sample, one different phrasing, and it flips. Yet the loss already treats this pair as most of the way home.

The edit: subtract a constant before the sigmoid

// DPO: loss = −log sigmoid( gap )
// SimPO: loss = −log sigmoid( gap − γ )
 
// Read it as a moved finish line: the loss now behaves as though
// "zero" is at gap = γ. A pair is only "solved" once the winner
// leads by γ, not by any positive amount.

Run it on the page-1 numbers (gap = +0.60, γ = 1.0)

argument to sigmoidsigmoidloss = −log(·)push = 1 − sigmoid
without γ0.600.6460.4370.354
with γ = 1.00.60 − 1.0 = −0.400.4010.9130.599

Read the last column. The winner is already ahead (gap +0.60), and without γ the loss has largely lost interest. With γ = 1.0 the pair is still treated as unfinished, and the push is 70% stronger. Training keeps working on this pair until the lead is convincing.

Where you have met this idea before

Chapter 5 tab 4 made the point that the Bradley-Terry loss has no stop gate: sigmoid never reaches 1, so the loss shrinks forever and "done" is never expressed in the objective. γ does not remove that, but it does something useful with it — it says where the interesting region ends:

MethodWhat it targets
DPOgap > 0, pushed forever, weaker and weaker
SimPOgap > γ — a stated, finite goal
IPO (ch. 6 variants table)same complaint, different cure: a squared loss with a finite optimum

Two papers, one diagnosis: an unbounded objective on a fixed dataset overtrains. SimPO moves the finish line; IPO changes the shape of the track.

The Whole Loss, and When to Reach For It

All three edits in one line

loss = −log sigmoid[ (β/|y_w|)·log P(y_w|x) − (β/|y_l|)·log P(y_l|x) − γ ]
 
// └──────── score(winner) ───────┘ └──────── score(loser) ────────┘
//
// y_w, y_l = winning / losing response |y| = its token count
// P = the CURRENT policy only — no P_ref anywhere
// β = scale (how many "reward units" per unit of avg log-prob)
// γ = target margin (the moved finish line)

Compare to ch. 6’s DPO loss and you can point at every difference: two divisions by |y|, two deleted P_ref terms, one subtracted γ.

Hyperparameters, and what each one does when you turn it

knobpaper's rangewhat it controlstoo largetoo small
β2.0 – 2.5how many reward units one unit of average log-prob is worth — i.e. the scale of the gap fed to sigmoidsigmoid saturates, pairs go quiet earlygaps stay near 0, weak discrimination
γ0.5 – 1.5how big a lead counts as "done"never satisfied — keeps pushing, drift risk (no reference to stop it)reverts toward plain DPO behavior

Note β is much larger than DPO’s typical 0.1. That is expected, not a contradiction: it multiplies an average log-prob (a number around −0.7 per token) rather than a log-ratio (a number around ±0.2), so it needs a bigger scale to produce comparable gaps.

Review questions on this chapter

QuestionOne-line answer
"Why is SimPO reference-free — isn't that dangerous?"Length normalization takes over the reference's comparability job; what you genuinely lose is its anchoring job, and that is covered only by the SFT init, a short low-LR run, and γ.
"What's the actual bug in DPO that SimPO names?"DPO optimizes a total, reference-relative log-ratio while decoding ranks by average per-token log-prob — the paper measures agreement between the two rankings at only ~50%.
"Why does SimPO resist length inflation?"Padding with average-quality tokens leaves an average unchanged; you can only raise a mean by adding tokens better than the current mean.
"Why is β ~2 here but ~0.1 in DPO?"Different units — it scales a per-token average (≈−0.7) instead of a log-ratio (≈±0.2).
"What does γ buy?"It moves the finish line from "ahead by anything" to "ahead by γ", so noise-sized leads are not treated as solved.
